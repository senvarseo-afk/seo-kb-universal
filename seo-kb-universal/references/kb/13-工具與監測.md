# 13. 工具與監測

> 版本：1.1 ｜ 更新日期：2026-11-05 ｜ 適用：所有 SEO 網站專案 ｜ 撰寫：Claude

## 本章摘要

1. Google Search Console（GSC）是唯一能看到 Google 自己怎麼看你網站的工具；每個報表都有固定的「判讀順序」，本章逐一列出各狀態的意義與處理方式。
2. GSC 介面只給 16 個月、1,000 列資料；超過三個站或需要長期趨勢，一律用 Bulk data export 到 BigQuery，再接 Looker Studio。
3. GA4 只需要做對四件事：事件命名、Key events、連結 GSC、把資料保留期從 2 個月改成 14 個月（預設值會讓你損失探索報表資料）。
4. 工具不是越多越好：起步期（1–3 站）每月約 US$0–60，成長期約 US$150–350，多站 / 程序化規模約 US$400–900；本章給出每階段的最小必要組合。
5. 監測的核心是「頻率 + 門檻 + 動作」：每日看索引與 GSC 異常、每週看成效與 CWV、每月做對照分析；每個門檻都要對應一個預先寫好的處理流程。

## 13.1 Google Search Console 完整用法

依 Google 官方說明，收集到的資料通常在 2–3 天內出現在報表（https://support.google.com/webmasters/answer/7576553）；超過 48 小時未更新時暫停判讀。

### 13.1.0 資源類型與驗證

**規範**：每個網站同時建立「網域資源（Domain property）」與主要的「網址前置字元資源（URL-prefix property）」；多語言站的各語言子目錄另建 URL-prefix 資源以利分別檢視。

**為什麼**：Domain property 彙整 http / https / www / 子網域全部資料；HTTPS 報表僅對 Domain property 與 HTTPS URL-prefix 顯示；URL 檢查配額以 property 為單位。URL-prefix 資源可當作「資料夾層級的篩選器」。

**怎麼做**：Domain property 用 DNS TXT 驗證；多語言站為 `/ja/`、`/id/` 等各建 URL-prefix；Owner 至少兩人，外包只給「受限（Restricted）」。

**驗收方式**：設定 → 「使用者和權限」至少 2 位 Owner；設定 → 「關聯」可看到 GA4 資源。

**常見錯誤**：只建 URL-prefix 導致漏看 http 與 www 版本的問題；用 GTM 驗證後拿掉容器導致驗證失效。

### 13.1.1 成效（Performance）報表

**規範**：所有成效判讀以「相同時間區間的比較（Compare）」為基礎，並且每一次分析都先確認右上角「上次更新」時間，再看數字。

**為什麼**：
- 介面保留 **16 個月**資料，超過即永久消失（來源：GSC 說明中心「成效報表」，查閱 2026-11-03）。
- 最新資料為「初步資料（dotted line）」，數小時內仍會變動。2025-12 起新增 **週 / 月檢視**，既有 **24 小時檢視（hourly）**；Google 同時承認成效報表時常**嚴重延遲**，2026-10 曾超過 64 小時（來源：Search Engine Roundtable 2025-12-09、2026-10-11，查閱 2026-11-03）。
- 搜尋類型：Web（text-based）、Web（multimodal，如 Google Lens）、Image、Video、News；Discover 與 Google News 為左側獨立報表。
- 2026-06-03 起新增 **Search Generative AI performance reports**（Search 與 Discover 各一份），只有「曝光」，維度 Pages / Countries / Devices（Discover 無）/ Dates；2026-08-31 全球開放。AI Overviews / AI Mode 的點擊仍混在一般報表（來源：Google Search Central Blog 2026-06-03，查閱 2026-11-03）。

**怎麼做（判讀順序）**：
1. 先看「上次更新」；超過 48 小時就暫停判讀。
2. 開「比較」：本週 vs 上週、近 28 天 vs 前 28 天、同期去年（看季節性）。
3. 從 **Pages** 分頁開始：匯出算出點擊跌幅最大的 10 個 URL，再對每個 URL 看 Queries 找掉的字。
4. 看 **Search appearance**：只用來看 rich result 類型的變化（此維度沒有 AI Overview 篩選項）；AI 曝光要看獨立的 Search Generative AI performance report，且目前只有曝光（來源：https://support.google.com/webmasters/answer/17011259 、https://support.google.com/webmasters/answer/16984139 ，查閱 2026-11-03）。
5. 看 **Countries** 與 **Devices**：東南亞站務必分國家，各國的跌通常不同步。
6. 「位置」在圖表是全站平均、在表格是該列平均，不要互比；查詢會被匿名化，表格加總永遠小於圖表總數。

**驗收方式**：每週匯出「Pages × 近 28 天 vs 前 28 天」；跌幅 > 25% 的 URL 進入處理流程（詳 12-狀況與解法手冊.md）。

**常見錯誤**：只看 Queries 不看 Pages（排名掉可能只是 SERP 加了 AI Overview）；用 3 個月預設視窗比較核心更新前後（應以 7–14 天對照視窗）；把 24 小時檢視的 hourly 資料當最終值。

### 13.1.2 網頁索引（Page indexing）報表

**規範**：每週檢視「未編入索引（Not indexed）」各原因的數量趨勢；優先處理「來源 = 網站（Source: Website）」的項目，但重要頁面即使來源是 Google 也要檢查（來源：https://support.google.com/webmasters/answer/7440203 ，查閱 2026-11-03），並以 URL 檢查工具抽樣至少 3 個 URL 確認報表未過時。

**為什麼**：Google 明說「未編入索引不一定是壞事」；範例列表上限 1,000 列且不保證完整；驗證修正約需兩週；問題在最後實例消失後仍停留 90 天。「2026-06-11 起本報表長時間凍結／延遲」僅見於第三方報導（TechWyse / Relevant Audience 2026-07）；Google 的資料異常頁（support.google.com/webmasters/answer/6211453，查閱 2026-11-03）在網頁索引報表下為「No recent issues」，截至查閱日未列任何對應條目（不能由目前頁面推斷歷來從未公告）；該頁 2026 年唯一相關條目是 2026-06-24 Discover 點擊／曝光與 Discover 生成式 AI 曝光因記錄錯誤異常，與網頁索引報表無關（來源：https://support.google.com/webmasters/answer/6211453 ，查閱 2026-11-03）。遇到數字長期不動時仍以 URL 檢查工具抽樣為準。

**怎麼做：各狀態的意義與處理**（來源：Google Search Console 說明中心「Page indexing report」，查閱 2026-11-03）

| 狀態 | 意義 | 處理 | 優先級 |
|---|---|---|---|
| Server error (5xx) | 要求時伺服器回 5xx | 看主機日誌對應時間點；確認 CDN / WAF 沒有攔 Googlebot；修好後用 URL 檢查「要求建立索引」 | 高 |
| Redirect error | 轉址鏈太長、迴圈、網址過長或鏈中有空 URL | 用 Screaming Frog「Redirect chains」報告找出來，改成一跳 301 | 高 |
| URL blocked by robots.txt | robots.txt 封鎖抓取 | 若是刻意封鎖且不想索引：改用 noindex 並解除封鎖；若誤封：修 robots.txt 並以 robots.txt 報表確認 | 中 |
| URL marked 'noindex' | 頁面或 HTTP header 有 noindex | 若該頁應被索引：移除 noindex（常見於 staging 設定被帶到正式站、WordPress「阻擋搜尋引擎」勾選） | 高 |
| Soft 404 | 頁面顯示「找不到」但回 200 | 真的沒內容就回 404 / 410；有內容但太薄則補內容；分類頁為空時直接 noindex 或 404 | 中 |
| Blocked due to unauthorized request (401) | 要求授權 | 移除驗證或允許已驗證的 Googlebot；常見於 staging 的 basic auth | 高（若為正式站） |
| Not found (404) | 回 404 | 頁面已搬家 → 301；真的刪除 → 讓它 404 / 410，不要用 Removals 工具清；從內部連結與 sitemap 移除 | 低（除非量大） |
| Blocked due to access forbidden (403) | 回 403 | Googlebot 不會帶憑證，通常是 WAF / 主機 bot 防護誤判；放行 Google 官方 IP 範圍 | 高 |
| URL blocked due to other 4xx issue | 其他 4xx | 用 URL 檢查看實際回應碼 | 中 |
| Crawled – currently not indexed | 已抓取但未索引；日後可能索引，不需重新提交 | 表示 Google 抓過但未索引，常見是**品質 / 價值判斷**，但不能排除渲染、重複內容等技術因素，要用 URL 檢查工具確認（來源：https://support.google.com/webmasters/answer/7440203 ，查閱 2026-11-03）：補強獨特性、增加內部連結、合併相似頁、低價值頁 noindex。量大且持續成長是整站品質訊號不足的警訊 | 中–高（看比例） |
| Discovered – currently not indexed | 已發現但尚未抓取；Google 推遲以免網站過載 | 抓取預算 / 伺服器效能：看抓取統計的回應時間、減少無用 URL（facet、參數）、強化內部連結、確認 lastmod 準確 | 中–高（程序化站常見） |
| Alternate page with proper canonical tag | 替代版本正確指向已索引的 canonical | 不需處理 | 無 |
| Duplicate without user-selected canonical | 重複頁且無宣告 canonical，Google 自選 | 加 canonical；若是參數頁，在來源處理（詳 04-技術SEO規範.md） | 中 |
| Duplicate, Google chose different canonical than user | Google 不同意你的 canonical | 用 URL 檢查比對兩個 URL；常見原因：兩頁內容幾乎相同、hreflang 互指但內容未在地化、內部連結指向另一頁 | 中–高 |
| Page with redirect | 非 canonical 的轉址 URL | 不需處理；但若 sitemap 內有轉址 URL，要清掉 | 低 |
| Indexed, though blocked by robots.txt（警告） | 雖被封鎖仍索引，摘要受限 | 若不想被索引：解除封鎖 + noindex；若想被索引：解除封鎖 | 中 |
| Page indexed without content（警告） | 已索引但讀不到內容 | 檢查是否 cloaking、JS 渲染失敗、不支援的格式；用 URL 檢查看「已轉譯的 HTML」 | 高 |

**Sitemap 篩選器**：改成「所有已提交網頁」或指定 sitemap 可知「我希望被索引的頁」有多少真的被索引。**標準：已提交 URL 索引率 ≥ 90%**（流量站經驗值，非官方標準）；程序化站 ≥ 70% 可接受，< 50% 需檢視頁面品質（詳 11-流量站與程序化SEO.md）。

**驗收方式**：「已編入索引」÷ sitemap 提交數；Validate fix = Passed。

**常見錯誤**：對 Crawled – currently not indexed 反覆「要求建立索引」；把 1,000 列範例當完整清單；在報表凍結期間誤判索引驟降。

### 13.1.3 Sitemaps 報表

**規範**：每站提交一個 sitemap index；子 sitemap ≤ 50,000 URL 且未壓縮 ≤ 50 MB；`lastmod` 只在實質變更時更新；新聞站另提交 news sitemap（詳 20-新聞與時效型內容SEO.md）。

**為什麼**：Sitemaps 報表顯示「已發現的網頁數」與狀態（成功 / 有錯誤 / 無法擷取）；Google 多次表示若 `lastmod` 與內容變動不符就會忽略它。

**驗收方式**：狀態 = 成功；已發現網頁數 ≈ 有效 URL 數（誤差 < 5%）；「無法擷取」時先用 URL 檢查測試 sitemap 本身的 HTTP 狀態。

**常見錯誤**：sitemap 含 noindex、轉址、404、非 canonical URL；Yoast 與 RankMath 同時產出兩套 sitemap；每天把所有 lastmod 改成今天。

### 13.1.4 移除（Removals）

**規範**：Removals 只用於「緊急隱藏」；真正的移除以 404 / 410 / noindex / 密碼保護為準。

**為什麼**：暫時移除只隱藏約 **6 個月**，期滿後若頁面仍可索引「可能」重新出現；不阻止抓取；工具提供「Remove this URL only」與「Remove all URLs with this prefix」兩種範圍（來源：https://support.google.com/webmasters/answer/9689846 ，查閱 2026-11-03）。另有「清除摘要」（只移除描述直到重新索引）、「過時內容」分頁（非擁有者的 Refresh Outdated Content 申請）、「SafeSearch 篩選」分頁（被檢舉為成人內容的 URL，誤判可在 2–3 個月後申請覆審）（來源：GSC 說明中心「Removals tool」，查閱 2026-11-03）。

**怎麼做**：外洩 / 誤發布 → Removals 暫時移除 → 同時讓頁面 404 / 410 或 noindex → 確認 URL 檢查顯示「網址不在 Google 服務中」。

**常見錯誤**：用 Removals 清數千個舊 404；移除後忘記永久處理，半年後頁面「復活」。

### 13.1.5 體驗（Experience）：Core Web Vitals 與 HTTPS

**規範**：Core Web Vitals 報表「不良（Poor）」URL 群組數量須為 0，「需改善」在行動裝置上 ≤ 10% 的 URL 群組；HTTPS 報表的非 HTTPS URL 數 = 0。

**為什麼**：
- CWV 報表來自 CrUX 真實使用者，**28 天滾動**、取 **p75**；門檻：LCP 良好 ≤ 2.5 s / 不良 > 4 s、INP 良好 ≤ 200 ms / 不良 > 500 ms、CLS 良好 ≤ 0.1 / 不良 > 0.25。URL 依模板分群，群組狀態以最差指標為準；資料不足退回 origin 層級；行動與桌機分開；只列已索引 URL 且為抽樣（來源：GSC 說明中心「Core Web Vitals report」，查閱 2026-11-03）。
- 報表合併所有地區訪客：3G–4G 使用者多的站 LCP 會明顯較差。
- HTTPS 報表列出無法以 HTTPS 提供的 URL 與原因，只對 Domain property 與 HTTPS URL-prefix 顯示（來源：Google Search Central Blog 2022-09，查閱 2026-11-03）。
- 「行動裝置可用性」報表與「網頁體驗」總覽頁已於 2023–2024 年**移除**。

**怎麼做**：Poor 群組 → 範例 URL → PageSpeed Insights 看欄位與實驗室資料 → 修正後按「開始追蹤」進入 28 天驗證。

**驗收方式**：CWV 報表（行動）Poor = 0；PSI 真實使用者體驗三項皆綠。

**常見錯誤**：只修 Lighthouse 分數不修欄位資料；修完不按「開始追蹤」；以為 CWV 不良會直接「懲罰」排名（它是輕量訊號，但影響 Discover 與 Top stories 的呈現機會）。

### 13.1.6 購物、強化（Enhancements）與結構化資料報表

**規範**：所有「強化」類報表的「錯誤（Error）」數量 = 0；「警告（Warning）」允許存在但須每月檢視。

**為什麼**：GSC 只對偵測到且仍支援的類型產生報表（Breadcrumbs、Product snippets、Merchant listings、Review snippets、Videos 等）。**已停用**：Sitelinks searchbox、FAQ（2026-05 停止顯示）、HowTo（2023）、Practice problems（2025-11-05 公告、2026-01-06 移除）、Special announcements（2025-07-31）（來源：Google Search Central 文件更新記錄，查閱 2026-11-03）。「影片索引」為獨立報表。

**怎麼做**：錯誤 → 範例 URL → Rich Results Test 驗證 → 修正 → Validate fix。規範與範本詳 06-結構化資料規範.md。

**驗收方式**：各強化報表 Error = 0。

**常見錯誤**：仍放 FAQPage / HowTo 期待豐富摘要（白做工，但不會被懲罰）；把「警告」當錯誤硬修。

### 13.1.7 連結（Links）報表

**規範**：每月匯出「最熱門連結網站」與「最熱門的連結網頁」與上月比對，變動 > 30% 的來源人工看一次。

**為什麼**：這是唯一「Google 自己知道」的反向連結樣本，但只是 Google 已知連結的部分樣本、延遲數週；出現在報表不代表 Google 採計其排名權重，也不代表已過濾垃圾連結（來源：https://support.google.com/webmasters/answer/9049606 ，查閱 2026-11-03）。內部連結報表用來找「連結太少的重要頁」。

**怎麼做**：外部連結匯出前 1,000 個來源網域（與 Ahrefs 差異只是參考）；內部連結排序看 money page 是否在前 50，不在就補連結（詳 03-網站架構與資訊架構.md）。

**驗收方式**：重要頁的內部連結數在全站前 10%。

**常見錯誤**：看到負面連結就用 Disavow——演算法會自動忽略垃圾連結，Disavow 只有在同時符合兩條件時才用：大量垃圾／人為／付費連結指向你的站，且這些連結已造成或很可能造成手動處置；先嘗試請對方移除（來源：https://support.google.com/webmasters/answer/2648487 ，查閱 2026-11-03；詳 16-連結建設與數位公關.md）。

### 13.1.8 手動處置（Manual actions）與安全性問題（Security issues）

**規範**：兩個報表都必須是「未偵測到任何問題」；開啟 GSC 電子郵件通知給至少兩個收件人。

**為什麼**：手動處置是人工審查判定違反垃圾內容政策的處分（純垃圾、Site reputation abuse、不自然連結、結構化資料問題、偽裝等），導致整站或部分頁面降級或移除；Discover 政策違規也在此顯示。安全性問題則是被駭、惡意軟體、社交工程。

**怎麼做**：逐條看「受影響的網頁」→ 徹底修正（不只修範例 URL）→ 「要求重審」寫明原因、修正、預防；重審需數天到數週。政策詳 07-Google演算法與政策.md；被駭流程詳 12-狀況與解法手冊.md。

**驗收方式**：狀態回到「未偵測到任何問題」且收到重審通過信。

**常見錯誤**：修一半就申請重審；重審信辯解而非說明修正。

### 13.1.9 網址檢查工具（URL Inspection）

**規範**：每一個「索引異常」的判斷都先用 URL 檢查工具看「Google 索引」與「測試線上網址（Live test）」兩個結果，再下結論。

**為什麼**：它顯示索引中的版本（上次抓取時間、Google 選擇的 canonical、是否允許索引、Googlebot 類型）與即時測試（HTTP 回應、已轉譯 HTML、截圖、資源）。「要求建立索引」每資源每日有上限（未公布，實務約 10–12 次）且不保證索引。

**怎麼做**：貼 URL → 看是否在 Google 服務中與原因 → 比對「Google 選擇的標準網址」與「使用者宣告」→ 「測試線上網址」看已轉譯 HTML 是否含主要內容（JS 站必做）→ 看哪些資源被 robots.txt 封鎖。

**驗收方式**：Live test 的已轉譯 HTML 含完整正文與內部連結。

**常見錯誤**：把「要求建立索引」當發布流程（Google 沒有即時推送 API，Indexing API 僅限 JobPosting 與 BroadcastEvent；時效內容靠 sitemap + 內部連結）。

### 13.1.10 抓取統計資料（Crawl stats）與 robots.txt 報表

**規範**：每月看一次「抓取統計資料」（設定 → 抓取統計資料）：平均回應時間 < 300 ms、5xx 回應比例 < 1%、「主機狀態」為綠色。

**為什麼**：這是唯一能看到 Googlebot 抓取量、回應時間、回應碼、檔案類型、用途（探索 vs 重新整理）的地方；程序化站的 Discovered – currently not indexed 根因通常在此。robots.txt 報表（2023-11 取代舊測試工具）顯示 Google 看到的 robots.txt 版本。

**怎麼做**：回應時間突升 → 對照主機監控；「探索」占比突升 → 產生了大量新 URL（參數、分頁、標籤）；404 / 5xx 比例高 → 清理內部連結與 sitemap。

**常見錯誤**：把抓取總量下降直接解讀為降權（可能是網站變快或內容變動率低）。

### 13.1.11 建議（Recommendations）

**規範**：每週看一次總覽頁「建議」卡片；處理或明確標記「不採用」。2024-08 起 GSC 依網站狀況顯示建議（新增 sitemap、結構化資料機會、趨勢中的查詢等），只在有建議時顯示並定期重算（來源：Google Search Central Blog 2024-08，查閱 2026-11-03）。

### 13.1.12 API、Bulk data export 與 Looker Studio

**規範**：超過 1 個站、需要 > 16 個月趨勢、或需要完整查詢清單時，開啟 **Bulk data export 到 BigQuery**；Looker Studio 用 BigQuery 連接器而非 Search Console 連接器。

**為什麼**（來源：GSC 說明中心「Bulk data export」、Search Console API 限制文件，查閱 2026-11-03）：
- 介面匯出上限 1,000 列；Search Analytics API 每次最多 25,000 列（startRow 翻頁），配額每站 / 每使用者 1,200 QPM、每專案 30,000,000 QPD；URL Inspection API 每資源 **2,000 QPD / 600 QPM**。
- Bulk data export：每日自動把 Search 與 Discover 成效資料（含匿名化查詢彙總列）匯入 BigQuery；需 Cloud 專案啟用計費、授予 `search-console-data-export@system.gserviceaccount.com` BigQuery Job User 與 Data Editor；資料集名稱以 `searchconsole` 開頭；首次匯出最長 48 小時；**不含設定前的歷史資料**；資料無限累積除非設 partition expiration（≥ 14 天；流量站建議 3 年或不設）；更改 schema 會讓匯出失敗。
- 成本：BigQuery 免費額度每月 10 GB 儲存、1 TB 查詢，單站通常免費；多站 / 程序化大站約 US$5–30 / 月（經驗值）。
- Looker Studio：原生連接器受 API 列數與匿名化影響；BigQuery 連接器可做跨站、跨年與「品牌 vs 非品牌」自訂分組。

**怎麼做**：
1. GSC 設定 → Bulk data export → 填 Cloud 專案 ID（不是專案編號）→ 選資料集位置。
2. 48 小時後 BigQuery 出現 `searchdata_site_impression` 與 `searchdata_url_impression` 表。
3. Scheduled query 每日彙整成 `daily_summary` 小表（date, site, clicks, impressions, ctr, position, is_anonymized_query），Looker Studio 連小表以省查詢費。
4. 報表最少三頁：總覽（含年比）、頁面層級、查詢層級（品牌 / 非品牌 regex 分組）。

**驗收方式**：BigQuery 表每日新增 partition；Looker Studio 日期與 GSC 介面一致（允許延遲）。

**常見錯誤**：資料集未以 `searchconsole` 開頭；手動加欄位導致匯出停止；原生連接器同時用 Queries 與 Pages 當維度（匿名化查詢被過濾，數字對不上）。

## 13.2 GA4 必要設定

> Universal Analytics（UA）已於 2023-07-01 停止處理資料、2024-07-01 關閉存取，**已停用**；以下全為 GA4。

### 13.2.1 事件與 Key events

**規範**：每個站至少定義下列事件並標為 Key event（2024 年起 GA4 將「轉換（conversion）」改名為 **Key event**；標準資源最多 30 個 Key events）：

| 專案類型 | 必要 Key events |
|---|---|
| 內容站（AdSense / 聯盟） | `affiliate_click`（出站連結點擊，帶 `link_domain`、`page_location`）、`scroll`（90%）、`newsletter_signup`、`ad_click`（若用 GAM 可從 AdSense 連結取得） |
| 電商 | `purchase`、`add_to_cart`、`begin_checkout`（用 GA4 電子商務事件規格） |
| 企業官網 / SaaS | `generate_lead`、`form_submit`（分表單）、`sign_up`、`demo_request` |
| 本地商家 | `phone_call`（tel: 點擊）、`get_directions`、`form_submit` |

**為什麼**：GA4 連結 GSC 後，「Google 自然搜尋查詢（Queries）」報表只提供查詢與 Search Console 指標（點擊、曝光、CTR、排名），拿不到每個查詢的 Key events；要把行為／轉換對上搜尋，要看到達網頁層級的「Google 自然搜尋流量（Google organic search traffic）」報表，其轉換欄位才是 Key events（來源：https://support.google.com/analytics/answer/10737381 、https://support.google.com/analytics/answer/13682863 ，查閱 2026-11-03）；沒有 Key events 就無法回答「SEO 流量值多少」。

**怎麼做**：GTM 建事件；命名全小寫蛇形；GA4 管理 → 事件 → 標記為 Key event；聯盟站為 `affiliate_click` 設預設值（平均每次點擊收益）以便看「收益」欄。

**驗收方式**：DebugView 看到事件與參數；24 小時後「報表 → 參與 → 事件」出現。

**常見錯誤**：所有事件都標 Key event（稀釋）；GTM 與網站程式碼各送一次 `purchase`（重複計算）。

### 13.2.2 資料保留

**規範**：管理 → 資料設定 → 資料保留 → 事件資料保留改為 **14 個月**（標準資源最大值；預設是 2 個月），並開啟「在有新活動時重設」。

**為什麼**：資料保留只影響**探索（Explorations）與漏斗報表**，標準彙整報表不受影響；但 SEO 最常用的「頁面 × 來源 × 時間」自訂探索在 2 個月設定下做不出年比。GA4 360 可到 50 個月；變更 24 小時後生效，縮短會刪除資料（來源：Google Analytics 說明「資料保留」，查閱 2026-11-03）。

**驗收方式**：探索報表可選 13 個月前的日期。

### 13.2.3 與 GSC 連結

**規範**：每個 GA4 資源連結一個 GSC 資源（一對一），並把「Search Console」報表集合發布到導覽。

**為什麼**：連結後可看「Google 自然搜尋查詢」與「Google 自然搜尋流量（到達網頁）」，把 GSC 曝光 / 點擊與 GA4 參與度 / Key events 對上同一到達網頁。

**怎麼做**：GA4 管理 → 產品連結 → Search Console → 選 GSC 資源與網站串流；報表 → 資料庫 → 發布「Search Console」集合。

**驗收方式**：GA4 左側出現「Search Console」區塊且有資料（需 48 小時）。

**常見錯誤**：GSC 資源與 GA4 串流網域不一致（URL-prefix 必須相符）。

### 13.2.4 其他必要設定

- **內部流量篩選**：定義內部 IP 並把篩選器從「測試」改為「有效」。
- **參照連結網址排除**：金流 / 登入服務網域。
- **自訂維度**：`author`、`category`、`content_type`、`publish_date`（內容站必加）。
- **BigQuery 匯出**：免費版可每日匯出；與 GSC 放同一 Cloud 專案，用 `page_location` join。
- **Consent Mode v2**：Google 的 EU 使用者同意政策適用 EEA、英國與瑞士使用者，這些流量須以 Consent Mode 或 TCF 送出同意訊號；台灣不在該政策範圍，但仍須遵守當地個資法規（https://support.google.com/google-ads/answer/16724512 ，查閱 2026-11-04；廣告端見 22 §2.6、23 §5.1）。

## 13.3 Bing Webmaster Tools 與 IndexNow

**規範**：所有站都註冊 Bing Webmaster Tools（BWT）並啟用 IndexNow；台灣 / 東南亞 Bing 流量通常 < 3%，但 BWT 是免費的第二意見，IndexNow 同時餵給 Bing、Yandex、Naver、Seznam、Yep 等參與引擎。

**為什麼**（來源：Microsoft Bing Webmaster Blog 2024-03、2024-10、2025-03、2026-02；IndexNow.org，查閱 2026-11-03）：
- BWT 可從 GSC 匯入驗證；提供 Site Explorer（Bingbot 視角的目錄樹）、Site Scan（免費站內檢查，上限 10,000 URL）、Backlinks、Keyword Research、IndexNow Insights（2024-03）、Copilot 問答（2025-03 開放英文）、AI Performance 公開預覽（2026-02-10 官方公告：Total Citations、Average Cited Pages、Grounding queries 抽樣、頁面層級引用數與時間趨勢，涵蓋 Copilot、Bing AI 摘要與部分合作夥伴；2026-10-13 再加 Topics Portfolio beta）。成效資料歷史：官方部落格 2024-10-16 公告延長至 16 個月；「2025-08 延長至 24 個月（同時加國家／裝置篩選與關鍵字趨勢線）」僅見 Bing 團隊 Krishna Madhavan 的 LinkedIn 貼文與第三方報導（Search Engine Roundtable 2025-08-08、Search Engine Land），Bing Webmaster Blog 無對應文章，屬第三方報導、未見官方部落格證實。
- IndexNow：根目錄放 `{key}.txt`（8–128 字元英數與連字號），對 `https://api.indexnow.org/indexnow` 送 GET（單一 URL）或 POST JSON（每次最多 **10,000** URL）；200 成功、202 待驗證 key、403 key 無效、422 URL 不屬該主機、429 太頻繁。**Google 不參與 IndexNow**。

**怎麼做**：WordPress 用 Yoast / RankMath 內建；自建站在發布 / 更新 / 刪除 hook 呼叫 API；Cloudflare Crawler Hints 可代送。

**驗收方式**：BWT「IndexNow Insights」顯示每日提交量與被抓取數。

**常見錯誤**：cron 每次重送全站 URL（429）；key 檔放子目錄卻提交全站 URL（422）。

## 13.4 爬蟲工具：Screaming Frog 與 Sitebulb

### 13.4.1 Screaming Frog SEO Spider

**價格**：免費版 500 URL；付費授權 **£199 / 年 / 使用者**（5–9 支 £189、10–19 支 £179、20 支以上 £169；官方頁另提供 USD / EUR 計價，金額依頁面當下顯示；來源：https://www.screamingfrog.co.uk/seo-spider/pricing/ ，查閱 2026-11-03）。Log File Analyser 另售（13.7）。

**規範**：每個站每月至少完整爬一次（JS 站用 JavaScript rendering 模式），並把下列報表存檔比對。

**關鍵用法**：
1. **Configuration → Spider**：勾 Crawl & Store 的 Images / CSS / JS / hreflang / Structured Data / Pagination；JS 站選 Rendering = JavaScript（Chrome），AJAX timeout 5 s。
2. **API 整合**：Configuration → API Access 接 GSC（抓每 URL 點擊 / 曝光 / 索引狀態）、GA4、PSI（CrUX 欄位資料）、Ahrefs / Moz；這讓「孤兒頁（有 GSC 流量但爬不到）」一鍵現形（Reports → Orphan Pages）。
3. **Custom Extraction**（Configuration → Custom → Extraction）：用 CSS Path / XPath / Regex 抓頁面上任意欄位：
   - 作者名：XPath `//span[@class="author-name"]/text()`
   - 發布日期：XPath `//meta[@property="article:published_time"]/@content`
   - 廣告單元數：XPath `count(//ins[@class="adsbygoogle"])`（Function 模式）
   - 字數：Regex 或用內建 Word Count
   - 聯盟連結數：XPath `count(//a[contains(@href,"amzn.to") or contains(@rel,"sponsored")])`
   - 多語言站：`//link[@rel="alternate"]/@hreflang` 與 `/@href`
4. **Custom Search**：搜尋頁面原始碼含特定字串（例如 `noindex`、舊品牌名、`lorem ipsum`、未替換的模板變數 `{{`）。
5. **必看報表**：Response Codes（3xx 鏈、4xx、5xx）、Canonicals（Non-indexable canonical、chain）、Directives、Hreflang（Missing return link）、Structured Data（Validation errors）、Inlinks 排序找「連結少的重要頁」、Crawl Depth 分布（目標：90% 頁面深度 ≤ 3）。
6. **Crawl comparison**（Mode → Compare）：比對兩次爬取差異，用於上線前後驗證。
7. **排程**（File → Scheduling）：每週自動爬並匯出到 Google Sheets。

**驗收方式**：Non-indexable 頁含 GSC 點擊者 = 0；Redirect chains = 0；hreflang 缺回鏈 = 0；深度 > 4 的頁面 < 5%。

**常見錯誤**：記憶體未調（建議 ≥ 8 GB 才爬 10 萬 URL）；不限速打掛主機（≤ 5 threads）；未接 GSC API 就判斷孤兒頁。

### 13.4.2 Sitebulb

**價格**：Lite（1 使用者、每次審核 10,000 URL）、Pro（可選 1–50 使用者、預設 500,000 URL、視電腦規格可達 200 萬）、Cloud 從 £95 / 月起；年繳省 15%，Pro 有 14 天試用；Lite / Pro 的基本月費在官方頁由前端動態載入，本次未能讀到數字（Pro 額外使用者 £7 / 月起；官方頁無法讀取完整數字，專案執行時以官方頁當下版本為準；來源：https://sitebulb.com/pricing/ ，查閱 2026-11-03）。

**關鍵用法**：Hints 把問題分級（Critical / High / Medium / Low）並附說明，適合交給非技術同事；Crawl Maps 視覺化架構；Near-duplicate 偵測直觀；Custom Extraction 支援 XPath / CSS；可排程並比較歷次審核。

**選擇建議**：一人工作室只買 Screaming Frog；要給客戶 / 老闆看報告或多站排程才加 Sitebulb。

| PageSpeed Insights（PSI） | 欄位（CrUX 28 天 p75）+ 實驗室（Lighthouse） | 單一 URL 的真實使用者 vs 實驗室對照 | 欄位資料需足夠流量，否則退回 origin |

| CrUX Dashboard（Looker Studio 範本） | 欄位（BigQuery 月資料） | 月趨勢、與競爭者 origin 比較 | Google 宣布由 **CrUX Vis**（2024-10 起，資料來自 History API，週資料）逐步取代；官方 CrUX Dashboard 文件已標示 **deprecated**（已棄用，未給下線日期，仍可存取），並建議改用 CrUX Vis（來源：https://developer.chrome.com/docs/crux/dashboard ，查閱 2026-11-03）；新專案一律用 CrUX Vis |
| CrUX API / History API | 欄位 | 自動化監測、排程寫入 BigQuery | 免費；History API 預設回傳 25 筆、最多 40 筆每週 collection period（`collectionPeriodCount: 40`），每筆涵蓋滾動 28 天（來源：https://developer.chrome.com/docs/crux/history-api ，查閱 2026-11-03） |
| Lighthouse（DevTools / CLI / CI） | 實驗室 | 找具體修正項目、CI 阻擋退步 | 分數波動 ±5–10，不要盯分數 |
| WebPageTest | 實驗室（真實裝置、地點） | 瀑布圖、filmstrip、可選東南亞節點 | 免費額度有限，付費起價第三方整理約 US$20 / 月（webpagetest.org 價格頁本次無法讀取，專案執行時以官方頁當下版本為準） |
| Chrome DevTools Performance | 實驗室（本機） | INP 元兇、Layout shift 來源 | 用 Interactions 與 Layout Shifts 軌道 |
| web-vitals.js | 欄位（自家 RUM） | 送 GA4 當事件，看每頁 / 裝置 / 國家的 CWV | 補 CrUX 抽樣不足的最佳方案 |

**規範**：修 CWV 順序固定：CrUX 欄位找「哪裡」→ Lighthouse / DevTools 找「為什麼」→ PSI 實驗室確認 → 等 28 天看欄位。修法詳 04-技術SEO規範.md。

**常見錯誤**：拿 Lighthouse 100 分當成果；在台灣光纖測速後宣稱東南亞體驗良好。

## 13.7 日誌分析工具

**規範**：程序化站、超過 5 萬 URL、或大量 Discovered – currently not indexed 的站，每季至少做一次 30 天日誌分析。

**為什麼**：GSC 抓取統計只有彙總與 1,000 列範例；日誌能看到 Googlebot 實際抓了哪些 URL、多常回來、預算花在哪些無用 URL 上。

**工具**：
- **Screaming Frog Log File Analyser**：官方價格頁 **£99 / 年 / 授權**（來源：https://www.screamingfrog.co.uk/log-file-analyser/pricing/ ，查閱 2026-11-03），免費版 1,000 筆；可匯入爬取結果做「爬到但沒被抓 / 被抓但爬不到」比對。
- **自建**：Cloudflare Logpush → BigQuery，或 Nginx log → GoAccess / ELK；篩 `user_agent LIKE '%Googlebot%'` 並驗證 Googlebot 以過濾假 Googlebot：反向 DNS 確認網域為 `googlebot.com` / `google.com` / `googleusercontent.com` 後，再正向解析回原 IP；或直接比對官方 IP ranges JSON（來源：https://developers.google.com/crawling/docs/crawlers-fetchers/verify-google-requests ，查閱 2026-11-03）。
- **Botify / Lumar / OnCrawl**：企業級，流量站不需要。

**驗收指標**：Googlebot 請求 200 回應 ≥ 90%；抓取量前 20% 的 URL 是你想被索引的頁；「可索引且在 sitemap 但 30 天未被抓」的 URL < 10%。

**常見錯誤**：未驗證 UA；只看 CDN 日誌漏掉直連請求。

## 13.8 排名追蹤工具

**規範**：只追蹤「決策會用到」的關鍵字：每個站核心字 50–300 個，分國家 / 裝置；每日追蹤只在核心字，其餘每週。

**為什麼**：GSC 平均位置是所有曝光的平均，無法回答「這個字在台北手機上第幾名」；但追蹤器是 SERP 抓取估計，且 AI Overview 出現時第 1 名的點擊率可能只剩一半，排名要和 GSC 點擊一起看。

**工具與價格級距（第三方整理，2026-11-03 查閱，採購前確認官方）**：Wincher 約 $24–29 / 月起（500 字）、SE Ranking Core 約 $65–129 / 月（2,000 字每日）、AccuRanker 約 $116–249 / 月起、Nozzle 約 $99 / 月起（按 SERP 量計費，適合程序化站）；Ahrefs Lite 內建 750 字、Semrush SEO 方案 500 字。

**設定要點**：分國家 / 語言、分裝置、記錄 SERP 特徵（AI Overview、Top stories、PAA）、記錄排名 URL（偵測內部競食）。

**驗收方式**：追蹤器的 URL 與 GSC Pages 分頁中該字的主要頁一致。

**常見錯誤**：每日追蹤 5,000 個長尾字看噪音；只看平均排名不看前 3 / 前 10 名字數變化。

### 13.9.2 告警怎麼設

**方案 A（零成本，單站）**：Google Sheets + Apps Script 每日呼叫 Search Analytics API（`searchanalytics.query`，`dataState: 'all'`）抓前 3 天資料；計算「最新完整日 vs 前 7 日同星期平均」，低於 −30% 就 `MailApp.sendEmail`；同一腳本用 `urlInspection.index.inspect` 抽查 20 個重點 URL。

**方案 B（BigQuery + Looker Studio，多站）**：Bulk data export 寫入 BigQuery 後，Scheduled query 每日算每站的異常旗標：
```sql
WITH d AS (
  SELECT site_url, data_date, SUM(clicks) clicks
  FROM `proj.searchconsole.searchdata_site_impression`
  WHERE data_date >= DATE_SUB(CURRENT_DATE(), INTERVAL 70 DAY)
  GROUP BY 1,2
), base AS (
  SELECT site_url, data_date, clicks,
    AVG(clicks) OVER (PARTITION BY site_url, EXTRACT(DAYOFWEEK FROM data_date)
                      ORDER BY data_date ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING) AS avg_same_dow
  FROM d
)
SELECT site_url, data_date, clicks, avg_same_dow,
       SAFE_DIVIDE(clicks, avg_same_dow) - 1 AS delta
FROM base
WHERE data_date = (SELECT MAX(data_date) FROM d)
  AND SAFE_DIVIDE(clicks, avg_same_dow) - 1 < -0.30
```
結果用 Cloud Functions / Apps Script 讀取再發 Slack / Email；或在 Looker Studio 用條件格式標紅並設「排程電子郵件」每日寄出（Looker Studio **沒有**原生門檻告警，排程寄送是最接近的替代）。

**方案 C（第三方）**：SEOTesting、Semrush Position Tracking 排名變動通知、Ahrefs Alerts（連結 / 提及）；約 US$30–100 / 月。

**規範**：每條告警都要有 runbook（誰、多久內、做哪三步）；一週誤報超過 3 次就調門檻。
