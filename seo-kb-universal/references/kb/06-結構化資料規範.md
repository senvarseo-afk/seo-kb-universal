# 06 結構化資料規範

> 版本：1.1 ｜ 更新日期：2026-11-05 ｜ 適用：所有 SEO 網站專案 ｜ 撰寫：Claude

## 本章摘要

1. 結構化資料的作用是「讓 Google 明確理解頁面實體」並取得 rich result 資格；它不是排名因素，標記正確也不保證顯示。
2. 截至 2026-11，Google 搜尋圖庫列出 25 種支援功能；FAQ（2026-05）、HowTo（2023-09）、Sitelinks search box（2024-11）、Course info / Estimated salary / Learning video / Vehicle listing（2025-09）、Special announcement（2025-07-31 起停用）、Practice problem（2025-11-05 公告、2026-01-06 移除）已退場，Breadcrumb 僅桌機顯示（2025-01），Dataset 僅用於 Dataset Search（2025-11）。
3. 一律使用 JSON-LD，以 `@graph` + `@id` 串接 `Organization` / `WebSite` / `WebPage` / `Person` / 主要內容類型，全站只維護一套實體定義。
4. 只標記頁面上可見、真實、屬於該頁的內容；造假評論、標記隱藏內容會導致結構化資料手動處置（失去 rich result 資格，不影響排名）；自評自家企業的星等（自家商家的評論標記）則是「不符合星等展示資格」而不顯示星等，不會僅因此被手動處置，但虛構評分仍屬違規（https://developers.google.com/search/blog/2019/09/making-review-rich-results-more-helpful#faq）。
5. 驗收用 Rich Results Test（資格）+ Schema Markup Validator（語法）+ GSC 增強功能報表（全站錯誤趨勢），每次發布與每月各跑一次。

## 1. JSON-LD 原則與放置位置

**規範**：所有結構化資料以 JSON-LD 格式、放在 `<head>` 內（或 `<body>` 皆可）的單一 `<script type="application/ld+json">` 區塊中，使用 `@graph` 描述頁面上所有實體；每個實體有穩定的 `@id`；內容必須與頁面可見內容一致。

**為什麼**：Google 一般指南明列三種格式（JSON-LD、Microdata、RDFa），並「建議使用 JSON-LD」；JSON-LD 可與 HTML 分離、容易由 CMS 動態注入、易於驗證。Google 可以讀取由 JavaScript 注入的 JSON-LD（需在轉譯後存在於 DOM），但伺服器端輸出最可靠（來源：Google Search Central〈Structured data general guidelines〉，查閱 2026-11-03）。

**怎麼做**：
- 位置：`<head>` 優先；若 CMS 限制可放 `<body>` 結尾，Google 都能讀。
- 單一區塊 + `@graph`：避免多個區塊分別宣告同一實體造成重複（例如 SEO 外掛與主題各輸出一份 `Organization`）。
- `@id` 命名慣例：`https://example.com/#organization`、`https://example.com/#website`、`https://example.com/author/alex-chen/#person`、`{頁面URL}#webpage`、`{頁面URL}#article`。`@id` 是識別碼，不需可存取，但用該頁 URL 加片段最穩定。
- `@context` 固定為 `https://schema.org`。
- 必要屬性以 Google 文件為準（schema.org 本身沒有「必要」概念）；建議屬性盡量補齊。
- 日期一律 ISO 8601 含時區：`2026-11-03T09:00:00+08:00`。
- URL 一律絕對路徑、與 canonical 一致（含 trailing slash 規則）。
- JSON-LD 內是否放 HTML 依各類型規格決定：多數類型的 `description` 中標籤會被忽略，但 `JobPosting.description` 要求 HTML（https://developers.google.com/search/docs/appearance/structured-data/job-posting#structured-data-type-definitions）；保留 HTML 時要做安全序列化（跳脫 `</script`、引號與換行）。
- 不要被 robots.txt / noindex 封鎖含結構化資料的頁面或其圖片 URL。
- 動態內容（價格、庫存、評分）由同一資料源輸出到頁面與 JSON-LD，避免不一致。

**驗收方式**：Rich Results Test 顯示「偵測到 N 個有效項目」；URL 檢查工具「已檢索的網頁 → 更多資訊 → 結構化資料」確認 Google 實際讀到；GSC 增強功能報表無「錯誤」。

**常見錯誤**：JSON 語法錯誤（尾逗號、單引號）導致整段失效；同一頁兩套衝突的 `Organization`；JSON-LD 中的價格與頁面不同；用 `Thing` 當作者類型。

## 2. Google 目前支援的 rich result 類型（2026-11 查證）

來源：Google Search Central〈Structured data markup that Google Search supports〉搜尋圖庫（查閱 2026-11-03），共 25 項。「專案適用」為本知識庫的建議。

| # | 功能 | 主要 schema.org 類型 | 顯示形式 | 專案適用 |
|---|---|---|---|---|
| 1 | Article | `Article` / `NewsArticle` / `BlogPosting` | 頭條、Discover、「熱門報導」的標題/圖片/日期；一般結果無視覺差異 | 內容站、新聞、企業部落格（必備） |
| 2 | Breadcrumb | `BreadcrumbList` | 結果中以路徑取代 URL（**僅桌機**，2025-01 起） | 所有 |
| 3 | Carousel | `ItemList` + Recipe / Course list / Restaurant / Movie | 主機型輪播（限 4 種搭配類型） | 食譜站、課程站 |
| 4 | Course list | `Course` + `ItemList` | 課程列表輪播 | 教育、SaaS 學習中心 |
| 5 | Dataset | `Dataset` | **僅 Dataset Search**（2025-11 起不再用於一般搜尋） | 研究、數據型內容站 |
| 6 | Discussion forum | `DiscussionForumPosting` | 「討論與論壇」區塊 | 論壇、UGC 社群 |
| 7 | Education Q&A | `Quiz` / `Question` | 教育問答輪播（含英、西、越、葡等語言） | 教育 |
| 8 | Employer aggregate rating | `EmployerAggregateRating` | 雇主評分 | 求職平台 |
| 9 | Event | `Event` | 活動列表（日期、地點） | 活動、本地商家 |
| 10 | Image metadata | `ImageObject`（`creator`、`creditText`、`license`） | Google Images 的作者/授權資訊、「可授權」標籤 | 攝影、圖庫 |
| 11 | Job posting | `JobPosting` | Google 工作搜尋 | 求職 |
| 12 | Local business | `LocalBusiness` 子類型 | 知識面板、商家資訊（需搭配 Google 商家檔案，詳見 17） | 本地商家、連鎖 |

| 14 | Movie | `Movie` | 電影輪播 | 影視 |
| 15 | Organization | `Organization` 及子類型 | 知識面板、商家資訊、Merchant 品牌檔案 | 所有（必備） |
| 16 | Product | `Product` + `Offer` / `AggregateRating` / `Review` | 商品摘要（價格、評分、庫存）與 Merchant listing | 電商、評論站、聯盟站 |
| 17 | Profile page | `ProfilePage` + `Person` / `Organization` | 討論區塊中的作者資訊；作者實體辨識 | 所有有作者的站（E-E-A-T） |
| 18 | Q&A | `QAPage` | 問答結果（限一問多答的 UGC 頁） | 論壇、問答平台 |
| 19 | Recipe | `Recipe` | 食譜卡、主機型輪播 | 食譜 |
| 20 | Review snippet | `Review` / `AggregateRating`（需嵌於支援類型） | 星等 | 評論、產品、本地商家（限他評） |
| 21 | Software app | `SoftwareApplication` | 評分、價格 | SaaS、工具站 |
| 22 | Speakable | `speakable` | Google Assistant 朗讀（新聞）；仍為 beta，只限美國、英文設定的 Google Home 裝置；手機 Assistant 逐步由 Gemini 取代（2026-09 時程為第三方報導），Speakable 是否仍生效待查證（https://developers.google.com/search/docs/appearance/structured-data/speakable ，查閱 2026-11-04；詳見 21 章 §5） | 新聞 |
| 23 | Subscription and paywalled content | `isAccessibleForFree` + `hasPart` | 讓 Google 區分付費牆與 cloaking | 訂閱媒體 |
| 24 | Vacation rental | `VacationRental` | 度假租屋列表（需 Google 合作） | 旅宿 |
| 25 | Video | `VideoObject`（+ `Clip` / `SeekToAction` / `BroadcastEvent`） | 影片結果、關鍵時刻、LIVE 標籤 | 影片為主要內容的頁面 |

另外：
- **Structured data carousels (beta)**：`ItemList` 搭配至少一種 `LocalBusiness`（含 `Restaurant` / `Hotel` / `VacationRental` 等子型）、`Product` 或 `Event`。地區與查詢類型（Google 文件，查閱 2026-11-03）：**EEA** — 飯店、度假租屋、地面交通、航班、本地商家、活動 / 導覽 / 體驗、產品（桌機與手機）；**土耳其**（2025-05 加入）— 僅飯店、度假租屋、本地商家；**南非**（2025-08 加入；2026-01 擴充）— 飯店、度假租屋、活動 / 導覽 / 體驗、航班、產品、食物外送、租車、巴士訂票。申請：服務 EEA / 土耳其使用者者填「Google Search aggregator features interest form」（航班另有 flight queries 表單；產品走 CSS 計畫）；南非商家填「South African Badging and Refinement Chips Interest Form」。不在 25 項主表內；**以使用者所在地判定：目前只對 EEA、土耳其、南非使用者的指定查詢類型開放；台灣等亞洲使用者不在範圍內，與網站或商家所在地無關**（來源：https://developers.google.com/search/docs/appearance/structured-data/carousels-beta ，文件日期 2026-09-11，查閱 2026-11-03）。
- **Merchant listing 延伸**：運送政策（2025-11 商家層級）、退貨政策、會員方案（loyalty program，2025-06）、`hasAdultConsideration`（2026-05）、`category`（2026-07）、特價期間 `validFrom` / `validThrough`（2026-07）。電商細節詳見 19。
- **Book actions**：2025-06-12 曾加退場橫幅，**2025-11-05 Google 移除該橫幅**（原因：Search 仍有功能使用此標記）；2026-11-03 查閱文件仍在、無退場字樣，但**僅限合作夥伴**（「limited to book providers with a wide selection of available books」，需填興趣表單並 onboarding、以 feed 提交）。不在圖庫 25 項主表內；一般內容站不適用。
- **ClaimReview**：2026-11-03 查閱文件仍在，頁面維持警示「We're phasing out support for ClaimReview markup in Google Search」，但 **Fact Check Explorer 工具仍支援**；不在圖庫主表內。Google 未公布 Search 端最終停用日期。

## 4. @graph 串接方法與全站實體架構

**規範**：全站共用一組「基底實體」（`Organization`、`WebSite`、主要 `Person`），每頁的 `WebPage` 與內容實體以 `@id` 引用它們，形成單一知識圖；不同頁面對同一實體的 `@id` 必須一致。

**為什麼**：Google 以實體為單位理解網站；一致的 `@id` 讓 Google 把文章作者、網站擁有者、商家、品牌關聯起來，支撐 E-E-A-T 的「Who」與知識面板。Google 指南允許「巢狀」或「以 `@id` 引用」兩種方式描述多個項目，並要求「主要實體反映頁面焦點」。

**怎麼做（分層）**：

```
層 1  全站基底（每頁都輸出，內容相同）
      Organization (#organization) ── logo (ImageObject #logo)
      WebSite      (#website)      ── publisher → #organization
層 2  頁面層（每頁不同）
      WebPage / CollectionPage / AboutPage / ContactPage ({url}#webpage)
         ├─ isPartOf → #website
         ├─ breadcrumb → BreadcrumbList ({url}#breadcrumb)
         ├─ primaryImageOfPage → ImageObject
         └─ about / mainEntity → 主要內容實體
層 3  內容實體（依頁面類型）
      Article / Product / Recipe / Event / LocalBusiness / ItemList …
         ├─ mainEntityOfPage → {url}#webpage
         ├─ author → Person (/author/xxx/#person)
         └─ publisher → #organization
層 4  作者實體（作者頁完整定義；文章頁在同一 graph 內提供 @id + @type + name + url）
      Person (/author/xxx/#person) ── 在作者頁以 ProfilePage.mainEntity 完整定義；Google 不會為了 @id 去抓另一頁補齊
```

## 5. 常用類型完整範本

以下範本皆為可放入 `@graph` 的物件（省略 `@context`），屬性依 Google 文件（查閱 2026-11-03）標註「必要 / 建議」。

### 5.1 Article / NewsArticle / BlogPosting

Google：無必要屬性；建議 `author`（Person/Organization，含 `name` 與 `url`）、`headline`、`image`（16:9、4:3、1:1，≥ 50K 像素）、`datePublished`、`dateModified`。`author.name` 只放姓名，頭銜用 `jobTitle`；多作者用陣列分開。
- `BlogPosting`：部落格型內容；`NewsArticle`：新聞（詳見 20，需搭配 Google News 政策）；`Article`：其他。
- `reviewedBy`（schema.org 屬性）可用於 YMYL 審閱者，但它定義在 `WebPage` 而非 `Article`，應放在關聯的 `WebPage` 節點上；Google 不顯示但不報錯（https://schema.org/reviewedBy）。
- 付費牆：`isAccessibleForFree: false` + `hasPart` 的 `WebPageElement` 指向 `cssSelector`。

見第 4 節完整範例。

### 5.2 Product（含 Offer、AggregateRating、Review）

Google 區分兩種：
- **Product snippets**（評論站 / 無法直接購買）：必要 `name` + 至少一項 `review` / `aggregateRating` / `offers`。
- **Merchant listing**（可在本站購買）：必要 `name`、`image`、`offers`（必須是 `Offer` 而非 `AggregateOffer`），`Offer` 必要 `price`（> 0）與 `priceCurrency`；建議 `availability`、`itemCondition`、`priceValidUntil`、`shippingDetails`、`hasMerchantReturnPolicy`、`validFrom`/`validThrough`（特價期間，2026-07 新增說明）。建議 `brand`、`sku`、`gtin`、`description`、`aggregateRating`、`review`、`category`（2026-07）、`hasAdultConsideration`（2026-05）。

- 聯盟站（非自售）：不要標 `shippingDetails` / `hasMerchantReturnPolicy`（不是你的政策）；`offers.url` 可指向聯盟連結目標頁或本頁購買區。
- `aggregateRating` 只能來自本站收集的評分；不可彙整其他網站（Google 明文禁止）。
- 2025-01-15 起 Google 建議只接受「附評論文字與作者姓名」的評分；2026-07-24 新增指南：不得包含假評論或未揭露的有償評論。
- 評論嵌套：巢狀於 `Product` 時不要再寫 `itemReviewed`（2025-11-12 Google 澄清「避免以多種方式指明被評對象」）。
- 變體：`ProductGroup` + `hasVariant` / `isVariantOf`（詳見 19）。

### 5.3 Organization（含 logo、sameAs、聯絡）

- 放在首頁或關於頁即可；用最具體子類型（`OnlineStore`、`NewsMediaOrganization`、`LocalBusiness` 子類型）。

Google `ProfilePage`：必要 `mainEntity`（Person 或 Organization）與其 `name`（或 `alternateName`）；建議 `dateCreated`、`dateModified`（人工編輯日期）、`description`（簡介/資歷）、`image`（非佔位圖）、`sameAs`、`alternateName`（帳號）、`identifier`、`interactionStatistic`、`agentInteractionStatistic`。頁面主要焦點必須是單一人物或組織。

作者頁：
```json
{

  "dateModified": "2026-09-15T00:00:00+08:00",
  "isPartOf": { "@id": "https://example.com/#website" },
  "mainEntity": {
    "@type": "Person",
    "@id": "https://example.com/author/alex-chen/#person",
    "name": "Alex Chen",
    "alternateName": "andy_travel",
    "url": "https://example.com/author/alex-chen/",
    "image": "https://example.com/img/alex-chen-400x400.jpg",
    "description": "旅遊編輯，常駐當地六年，實際辦理過觀光簽、延簽與居留證。",

    "knowsAbout": ["簽證申請", "東南亞長住"],

```

### 5.5 WebSite

```json
{
  "@type": "WebSite",
  "@id": "https://example.com/#website",
  "url": "https://example.com/",
  "name": "Example 旅遊指南",
  "alternateName": "Example 指南",
  "publisher": { "@id": "https://example.com/#organization" },
  "inLanguage": "zh-TW"
}
```
用途：網站名稱辨識（Google 使用 `WebSite.name` 作為 site name 來源之一）、title link 來源。**不要再加 `potentialAction: SearchAction`**（Sitelinks search box 已停用）。只放在首頁即可（全站放也無妨）。

### 5.6 WebPage 與子類型

子類型對應：首頁 `WebPage`、類別/列表 `CollectionPage`、關於 `AboutPage`、聯絡 `ContactPage`、作者 `ProfilePage`、FAQ 區塊所在頁仍用 `WebPage`（不用 `FAQPage`）、搜尋結果頁 `SearchResultsPage`（通常 noindex）。見第 4 節範例。

### 5.7 BreadcrumbList

必要：`itemListElement`（≥ 2 個 `ListItem`）；每個 `ListItem` 必要 `position`、`name`、`item`（最後一項可省 `item`）。依「使用者典型路徑」而非 URL 結構；首頁可省略。僅桌機顯示（2025-01 起）。見第 4 節範例。

### 5.8 VideoObject（含 Clip、SeekToAction、BroadcastEvent）

必要：`name`、`thumbnailUrl`、`uploadDate`（ISO 8601 含時區，首次發布日）；建議 `description`、`duration`（`PT1M54S`）、`contentUrl`（優先）或 `embedUrl`、`creator`（2026-09 新增，`Person`/`Organization` 含 `name`、`url`；`author` 亦可）、`interactionStatistic`、`expires`、`regionsAllowed`/`ineligibleRegion`（擇一）、`hasPart`（Clip）、`publication`（直播）。

```json
{
  "@type": "VideoObject",
  "@id": "https://example.com/videos/airport-arrival/#video",
  "name": "機場入境流程實拍（2026）",
  "description": "從下機到入境櫃台、掃碼、領行李的完整流程。",
  "thumbnailUrl": ["https://example.com/img/arrival-thumb-1280x720.webp"],
  "uploadDate": "2026-09-01T12:00:00+08:00",
  "duration": "PT8M20S",
  "contentUrl": "https://cdn.example.com/video/airport-arrival.mp4",
  "embedUrl": "https://www.youtube.com/embed/XXXXXXXXXXX",
  "creator": { "@id": "https://example.com/author/alex-chen/#person" },
  "interactionStatistic": {
    "@type": "InteractionCounter",
    "interactionType": { "@type": "WatchAction" },
    "userInteractionCount": 15230
  },
  "hasPart": [
    { "@type": "Clip", "name": "eTravel 掃碼", "startOffset": 95, "endOffset": 160,
      "url": "https://example.com/videos/taoyuan-airport-arrival/?t=95" },
    { "@type": "Clip", "name": "入境櫃台問答", "startOffset": 161, "endOffset": 300,
      "url": "https://example.com/videos/taoyuan-airport-arrival/?t=161" }
  ]
}
```
Clip 規則：影片 ≥ 30 秒、每段 `startOffset` 唯一、`url` 必須能深連結到該秒數、標記頁必須能觀看影片。`SeekToAction` 替代方式（Google 自動找關鍵時刻，限特定語言）：`"potentialAction": { "@type": "SeekToAction", "target": "https://example.com/videos/taoyuan-airport-arrival/?t={seek_to_second_number}", "startOffset-input": "required name=seek_to_second_number" }`。直播：`publication: BroadcastEvent` 含 `isLiveBroadcast: true`、`startDate`、`endDate`，並以 Indexing API 通知。

### 5.9 Event

必要：`name`、`startDate`（含時區）、`location`（`Place` 含 `address`；範本用實體 Place）；建議 `endDate`、`description`、`image`、`offers`（`price`、`priceCurrency`、`availability`、`url`、`validFrom`）、`performer`、`organizer`、`eventStatus`（`EventScheduled` / `EventCancelled` / `EventPostponed` / `EventRescheduled`）、`eventAttendanceMode`。2025-06 Google 移除了線上活動專屬屬性說明；`VirtualLocation` 在 schema.org 仍合法，但 Google Event rich result 的內容指南排除純線上活動、要求實體地點，純線上活動不符合資格（https://developers.google.com/search/docs/appearance/structured-data/event#content-guidelines）。

    "@type": "Place",
    "name": "台北國際會議中心 101 室",
    "address": { "@type": "PostalAddress", "streetAddress": "信義路五段 1 號", "addressLocality": "台北市", "postalCode": "110", "addressCountry": "TW" }

### 5.10 LocalBusiness

必要：`name`、`address`；建議 `@type` 用最具體子類型（`Restaurant`、`Dentist`、`Store`…）、`geo`、`telephone`、`url`、`openingHoursSpecification`、`priceRange`、`image`、`servesCuisine`、`menu`、`acceptsReservations`、`department`、`sameAs`（含 Google 商家檔案 URL）。自家商家不可標 `aggregateRating` / `review` 期待星等（自評限制）。與 Google 商家檔案的關係詳見 17。

```json
{
  "@type": "Restaurant",
  "@id": "https://example.com/#localbusiness",
  "name": "Example 台菜餐廳",
  "image": ["https://example.com/img/store-16x9.webp"],
  "url": "https://example.com/",
  "telephone": "+886-2-1234-5678",
  "priceRange": "$$",
  "servesCuisine": "Taiwanese",
  "address": { "@type": "PostalAddress", "streetAddress": "信義路五段 7 號", "addressLocality": "台北市", "postalCode": "110", "addressCountry": "TW" },
  "geo": { "@type": "GeoCoordinates", "latitude": 25.0330, "longitude": 121.5654 },
  "openingHoursSpecification": [
    { "@type": "OpeningHoursSpecification", "dayOfWeek": ["Monday","Tuesday","Wednesday","Thursday","Friday"], "opens": "11:30", "closes": "21:00" },
    { "@type": "OpeningHoursSpecification", "dayOfWeek": ["Saturday","Sunday"], "opens": "11:00", "closes": "22:00" }
  ],
  "sameAs": ["https://maps.app.goo.gl/XXXX"]
}
```

### 5.11 JobPosting

必要：`title`、`description`（HTML 允許、完整職缺描述）、`datePosted`、`hiringOrganization`（含 `name`；建議 `sameAs`、`logo`）、`jobLocation`（`Place` 含完整 `PostalAddress`）；遠端工作用 `jobLocationType: "TELECOMMUTE"` + `applicantLocationRequirements`；`validThrough` 有截止日期時必填、永不過期時省略（https://developers.google.com/search/docs/appearance/structured-data/job-posting）；建議 `baseSalary`（`MonetaryAmount` + `QuantitativeValue` 含 `unitText`）、`employmentType`、`identifier`、`directApply`。職缺過期必須移除標記或回 404/410，否則觸發手動處置。詳細政策見 Google〈Job posting〉文件。

### 5.12 Recipe

必要：`name`、`image`；建議 `author`、`datePublished`、`description`、`prepTime`/`cookTime`/`totalTime`（ISO 8601 duration）、`recipeYield`、`recipeCategory`、`recipeCuisine`、`keywords`、`nutrition.calories`、`recipeIngredient`（陣列）、`recipeInstructions`（`HowToStep` 陣列，含 `text`、可加 `url`、`image`；**此處的 HowToStep 仍可用**，退場的是獨立 HowTo rich result）、`aggregateRating`、`video`。2025-06 Google 澄清 Recipe 的 `image` 不影響一般文字結果的縮圖（用 `og:image`/`primaryImageOfPage`）。

### 5.13 SoftwareApplication

必要：`name`、`offers`（`price` 可為 0、`priceCurrency`）與至少一項 `aggregateRating` 或 `review`；建議 `applicationCategory`、`operatingSystem`、`screenshot`、`softwareVersion`、`downloadUrl`。網頁工具用 `WebApplication`（子類型）並設 `"operatingSystem": "Any"`、`"applicationCategory": "UtilitiesApplication"`。評分必須真實收集。

### 5.14 Dataset

必要：`name`、`description`（50–5,000 字元）；建議 `creator`、`license`、`distribution`（`DataDownload` 含 `contentUrl`、`encodingFormat`）、`temporalCoverage`、`spatialCoverage`、`keywords`、`isAccessibleForFree`、`citation`。2025-11 起僅供 Dataset Search；原創調查數據頁仍建議標記（Dataset Search 是學術與媒體引用來源，有助連結建設，詳見 16）。

### 5.15 ItemList（清單文 / 類別頁）

Google 僅在 Carousel（Recipe/Course/Restaurant/Movie）與 beta carousels 使用 `ItemList` 產生 rich result；一般「Best X」清單文標記 `ItemList` 不會有視覺效果，但有助 Google 理解列表項目（對 AI 功能擷取可能有幫助，待驗證）。兩種寫法：
- **摘要式**（項目在他頁）：`ListItem` 只含 `position` + `url`。
- **全部在本頁**：`ListItem` 含 `position` + `item`（完整 `Product` / `Place` 等）。

```json
{
  "@type": "ItemList",
  "@id": "https://example.com/best-power-banks/#list",
  "name": "2026 年 7 款最佳行動電源",
  "itemListOrder": "https://schema.org/ItemListOrderDescending",
  "numberOfItems": 7,
  "itemListElement": [
    { "@type": "ListItem", "position": 1, "name": "ACME X1", "url": "https://example.com/best-power-banks/#acme-x1",
      "item": { "@type": "Product", "name": "ACME X1", "image": "https://example.com/img/acme-x1-1x1.webp",
                "review": { "@type": "Review", "author": { "@id": "https://example.com/author/alex-chen/#person" },
                            "reviewRating": { "@type": "Rating", "ratingValue": 4.5, "bestRating": 5 } } } },
    { "@type": "ListItem", "position": 2, "name": "Beta P2", "url": "https://example.com/best-power-banks/#beta-p2" }
  ]
}
```
注意：不要在清單頁用 `AggregateRating` 評「整個清單」（Google：評論必須針對特定項目，不可針對類別或清單）。

## 6. 多語言站的注意事項

**規範**：每個語言版本頁面輸出該語言的結構化資料（`name`、`description`、`headline` 等文字欄位翻譯），`inLanguage` 標明語言；共用實體（`Organization`、`Person`）保持相同 `@id`，文字欄位可依語言不同；`url` / `@id` 指向該語言版本頁。

**為什麼**：Google 以頁面為單位處理結構化資料，文字欄位應與頁面語言一致（否則與「標記內容需在頁面可見」衝突）；實體 `@id` 一致讓 Google 把各語言版本的作者/品牌視為同一實體。hreflang 本身不放在 JSON-LD（詳見 10）。

**怎麼做**：
- `inLanguage` 用 BCP 47：`zh-TW`、`en-US`、`ja`、`vi`、`id`。
- `Organization.name` 可在各語言不同，但 `legalName`、`sameAs`、`@id` 相同；若品牌名跨語言不變則不翻譯。
- `Person.name` 保持原名（可加 `alternateName` 當地拼法）。
- 價格：`priceCurrency` 依市場（TWD、JPY、VND、IDR），價格與頁面顯示一致；多幣別頁面每幣別一個 `Offer`，`eligibleRegion` 標國家。
- 日期時區依市場（台灣 `+08:00`、越南 `+07:00`）。
- 翻譯 JSON-LD 中的文字欄位時，不要翻譯列舉值 URL（`https://schema.org/InStock`）、`@type`、屬性名。
- 文字欄位由翻譯流程統一產生（與頁面同源），避免頁面已翻譯但 JSON-LD 仍是原文。

**驗收方式**：每個語言版本各跑一次 Rich Results Test；Screaming Frog 擷取 `inLanguage` 與 `html lang` 比對。

**常見錯誤**：`@id` 含語言目錄導致同一公司被拆成 5 個實體（`/en/#organization`、`/zh/#organization`）——應統一用根網域 `@id`；JSON-LD `name` 是英文但頁面是越南文。

## 7. 驗證工具與監測

| 工具 | 用途 | 看什麼 | 頻率 |
|---|---|---|---|
| Rich Results Test（search.google.com/test/rich-results） | Google 是否能解析並判定 rich result 資格；支援轉譯 JS | 「偵測到的項目」、錯誤（紅，失格）、警告（黃，建議屬性缺） | 每次新模板上線、每次大改 |
| Schema Markup Validator（validator.schema.org） | schema.org 語法與屬性正確性（含 Google 不支援的類型） | 未定義屬性、型別錯誤 | 新類型開發時 |
| GSC URL 檢查工具 | Google 實際抓到的 HTML 與結構化資料（含 JS 轉譯後） | 「增強功能」區塊 | 排查單頁問題 |
| GSC 增強功能報表（每種 rich result 一份） | 全站有效 / 警告 / 錯誤數量趨勢 | 錯誤數突增（模板壞）、有效數驟降（Google 停用或模板改） | 每週看趨勢、每月審 |
| GSC 成效報表 → 搜尋外觀篩選 | 各 rich result 類型的曝光/點擊 | rich result 帶來的 CTR 差異 | 每月 |
| Screaming Frog（結構化資料 + 驗證） | 全站爬取、批次驗證、匯出 JSON-LD | 缺標記頁、驗證錯誤、`@id` 不一致 | 每季 |
| 瀏覽器擴充（Schema Builder、Detailed SEO） | 單頁快速檢視 | 開發時 | 隨時 |

GSC 報表已於 2025-09 起停止提供退場類型（Course info、Estimated salary 等）的報表；FAQ 報表 2026-06 起移除；若報表「消失」先對照第 3 節，不是你的錯。

**監測流程**：
1. 新模板：本機 → Rich Results Test（以「程式碼」模式貼 HTML）→ 上線 → URL 檢查即時測試 → 要求索引。
2. 每週：GSC 增強功能報表錯誤數比上週 +20% 以上 → 查最近部署。
3. 每月：成效報表「搜尋外觀」看各 rich result 的點擊占比；對照 Google 更新紀錄確認是否有功能退場。
4. 每季：Screaming Frog 全站驗證，列出「頁面類型 vs. 應有標記」矩陣的缺口。

## 8. 常見錯誤與警告

| 類型 | 訊息（GSC / RRT） | 原因 | 修正 |
|---|---|---|---|
| 錯誤 | 缺少欄位「name」/「image」/「offers」 | 必要屬性缺 | 補齊；Merchant listing 的 `image` 必要 |
| 錯誤 | 「offers」、「review」或「aggregateRating」其中之一應該要指定 | Product snippet 必要三選一 | 至少補一項真實資料 |
| 錯誤 | 「ratingValue」的值無效 | 用逗號小數、超出 best/worst 範圍 | 用點小數；`bestRating` 一致 |
| 錯誤 | 「price」無效 | 含貨幣符號或千分位 | 純數字 `1290` |
| 錯誤 | 「itemReviewed」缺少或重複 | 嵌套時又寫 itemReviewed | 嵌套時刪除 `itemReviewed` |
| 錯誤 | 「author」類型無效 | 用 `Thing` 或字串 | `Person` / `Organization` 含 `name` |
| 錯誤 | 剖析錯誤：缺少「,」或「}」 | JSON 語法 | 用 JSON linter；CMS 輸出時跳脫引號 |
| （RRT 不會對此顯示警告，須自行檢查） | 缺少「datePublished」/「dateModified」 | 建議屬性缺 | 補齊含時區；Article 文件說明 RRT 不會對缺少這兩個屬性發出警告，不能等 RRT 提示（https://developers.google.com/search/docs/appearance/structured-data/article） |
| 警告 | 缺少「aggregateRating」/「review」 | 建議屬性缺 | 沒有真實評分就忽略；不要造假 |
| 警告 | 「image」缺少多種長寬比 | 只給一張圖 | 提供 16:9、4:3、1:1 |
| 無提示但無效 | 標記的內容頁面上看不到 | 違反可見性 | 移除或讓內容可見 |
| 無提示但無效 | 圖片 URL 被 robots.txt 封鎖 | CDN 封鎖 | 開放抓取 |
| 無提示但無效 | `@id` 跨頁不一致 | 手寫差異 | 集中由程式產生 |
| 無提示但無效 | JSON-LD 僅由前端 JS 注入且轉譯失敗 | Google 轉譯逾時 | 伺服器端輸出 |
| 無提示但無效 | 語言不符（標記英文、頁面中文） | 模板未翻譯 | 第 6 節 |
| 過時 | 仍有 `FAQPage` / `HowTo` / `SearchAction` | 舊外掛 | 移除；不影響排名但徒增維護 |

警告不影響資格；錯誤會讓該項失格。優先處理「錯誤 > 可見性 > 警告」。

## 9. 違規結構化資料的手動處置與界線

**規範**：只標記「頁面上使用者看得到、真實、屬於該頁主題、由本站或真實使用者產生」的內容；不標記不存在的評分、不自評自家商家星等、不把無關類型套在頁面上、不對整個類別/清單做評分。

**為什麼**：Google〈Structured data general guidelines〉品質指南列出：內容須遵守 spam policies、資訊須最新、須原創、不標記使用者看不到的內容、不得誤導（假評論）、不得冒充他人；相關性（標記必須真實代表頁面）、完整性（頁面上所有同類項目都要標，如每則評論）、位置（放在描述的頁面上）、具體性（最具體類型）。違規會收到「結構化資料問題」手動處置：**該頁失去 rich result 資格，不影響網頁排名**；違反品質指南也可能讓 rich result 不顯示或被標記為垃圾（來源：Google Search Central〈Structured data general guidelines〉與〈Manual Actions report〉，查閱 2026-11-03）。

**界線表**：

| 行為 | 判定 | 說明 |
|---|---|---|
| 頁面沒有顯示評分，JSON-LD 有 `aggregateRating` | 違規 | 不可見內容 |
| 自家公司官網標 `Organization.aggregateRating` 4.9 | 不符合星等展示資格（自評） | 2019-09 起不顯示星等；不會僅因此被手動處置，但若評分是虛構的則屬違規（https://developers.google.com/search/blog/2019/09/making-review-rich-results-more-helpful#faq） |
| 把 Google 商家檔案的評分搬到官網 JSON-LD | 違規 | 不可彙整其他網站的評分 |
| 評論站標被評產品的 `Review`，頁面有可見評論 | 合規 | 這是 review snippet 的設計用途 |
| 聯盟站用 AI 產生「使用者評論」並標記 | 違規 | 假評論；2026-07 指南明文 |
| 有償評論且頁面明顯揭露 | 合規（需顯著揭露） | 2026-07 指南 |
| 文章頁套 `Product` 只為了星等 | 違規（相關性） | 頁面主題不是該產品 |
| 「Best X」清單頁對整個清單標 `AggregateRating` | 違規 | 評論須針對特定項目 |
| 類別頁標記每個商品的 `Product` 但無 `offers` 等資料 | 不建議 | Google 建議類別頁不要標完整 Product；用 `ItemList` 摘要式 |
| 頁面只顯示 3 則評論但標 300 則 | 違規（完整性） | 標記數 = 可見數，或連到完整頁 |
| 過期職缺未移除標記 | 違規 | JobPosting 專屬手動處置 |
| 用 `Event` 標記優惠活動 | 違規 | 非活動內容 |
| `Recipe` 標在非食譜頁 | 違規（相關性） | — |
| `Person` 作者用 AI 生成頭像與虛構資歷 | 違規（冒充/誤導） | 2026-10 Google 明文視為低品質 |

**收到手動處置的處理**：
1. GSC「手動處置」報表確認類型與範例 URL。
2. 全站同模板盤點，修正或移除標記（不是只改範例 URL）。
3. 提交重審請求，說明：違規原因、修正範圍（頁數）、防再發措施（例如評分改由真實使用者提交機制產生）。
4. 重審通常 1–3 週；期間 rich result 不顯示。

## 10. 結構化資料對 AI 搜尋的作用（簡述）

截至 2026-11-03 的狀態（細節與策略詳見 08）：
- Google 2026-05-15 新增〈Optimizing for generative AI features〉指南（同日並澄清垃圾政策同樣適用於 Search 的生成式 AI 回答）；2026-06-15 另在文件更新中澄清 Google 搜尋不需要、也不使用 `llms.txt`，有無該檔不影響排名（https://developers.google.com/search/updates#may-2026、#june-2026，查閱 2026-11-03）；兩者合起來表示：AI Overviews / AI Mode 的來源選擇基於與一般搜尋相同的索引、排名與品質系統，結構化資料「有助 Google 理解內容」但**不是 AI 引用的保證或專屬訊號**。
- 實務上的作用：`Organization` / `Person` 讓 AI 回答中的品牌與作者實體更準確；`Product` 的價格、庫存讓購物類 AI 回答抓到正確數值；`Article` 的日期讓時效判斷正確；`VideoObject` 的 Clip 讓影片片段被引用。
- 不要為了「餵 AI」堆砌無視覺效果的類型（例如全站加 `FAQPage`、`HowTo`、`Speakable`）；Google 的可見性原則仍適用：標記與頁面內容不符才有違規風險；與可見內容一致但已無 rich result 的標記只是無效，不算違規。
- 其他 AI 搜尋（ChatGPT、Perplexity 等）是否讀取 JSON-LD：各家未公開；OpenAI 與 Perplexity 的官方爬蟲文件只談 robots.txt 與可抓取的 HTML 內容，未提及 JSON-LD / schema.org（查閱 2026-11-03）；以「頁面內容清晰 + 實體一致」為主，結構化資料為輔。

## 11. 結構化資料 → 狀況解法表

| 症狀 | 可能原因 | 診斷步驟 | 解法 | 預防 |
|---|---|---|---|---|
| Rich Results Test 有效但 SERP 不顯示 | 顯示非保證；品質或信任不足；功能僅桌機；地區/語言限制；Google 判定頁面不相關 | 確認功能可用區域（第 2 節）；用桌機搜尋品牌 + 標題；GSC 搜尋外觀是否有曝光 | 補建議屬性、提升頁面品質（詳見 05）；等待 2–4 週 | 不承諾客戶「一定顯示」 |
| GSC 增強功能報表錯誤數突增 | 模板部署錯誤、外掛更新、CMS 輸出跳脫問題 | 看錯誤開始日期與部署紀錄；RRT 測範例 URL | 回滾或修正模板；修正後「驗證修正」 | 部署前 RRT 測試納入 CI |
| 增強功能報表「有效」數歸零 | Google 退場該功能（第 3 節）或報表移除 | 對照 Google 更新紀錄 | 移除過時標記，無需其他動作 | 每季對照更新紀錄 |
| 星等曾顯示現在消失 | 自評限制、評分造假被偵測、手動處置、改版後評論不可見 | GSC 手動處置報表；RRT 看 `aggregateRating` 是否仍有效；頁面是否顯示評論 | 修正可見性；移除自評；重審 | 評分只來自真實使用者提交 |
| 收到「結構化資料問題」手動處置 | 第 9 節界線違規 | 報表範例 URL + 全站盤點 | 修正所有同模板頁 → 重審請求 | 新模板上線前對照界線表 |
| Google 顯示的作者/發布者名稱錯 | `author.name` 含頭銜或出版社；多作者合併一個字串；`Person`/`Organization` 混用 | RRT 看 author 解析 | 依 Article 文件規範拆分 | 作者欄位由作者資料表產生 |
| 顯示的日期錯誤 | `datePublished` 無時區、與可見日期不同、全站 `dateModified` 被外掛改成同一天 | 比對 JSON-LD、可見日期、sitemap `lastmod` | 三者同源；停用自動改日期 | 更新流程含日期檢查 |
| 商品價格顯示舊價 | JSON-LD 與頁面資料源不同、快取 | RRT 即時測試 vs 快取頁 | 同一資料源輸出；更新後要求索引；Merchant Center feed 補強 | 價格變更觸發重新索引 |
| 麵包屑在行動版不顯示 | 2025-01 起僅桌機 | — | 正常現象 | — |
| 多語站 Organization 被拆成多個實體 | `@id` 含語言目錄 | 搜尋全站 `#organization` 出現幾種 | 統一根網域 `@id` | 由共用模組輸出 |
| JSON-LD 存在但 URL 檢查看不到 | 前端 JS 注入失敗、`<script>` 被其他 JS 移除、robots 封鎖 JS 檔 | URL 檢查「已轉譯的 HTML」搜尋 `ld+json` | 改伺服器端輸出；開放 JS 抓取 | SSR |
| 同一頁偵測到兩個 Organization | 外掛 + 主題各輸出 | 檢視原始碼 | 關閉其中一個來源 | 單一輸出點 |
| AI Overview 引用時品牌名錯誤 | 缺 `Organization` / `WebSite.name`、`sameAs` 不足 | 搜尋品牌看知識面板 | 補 `Organization`（含 `sameAs` 至 Wikidata/社群） | 基底實體完整 |
