# 03 網站架構與資訊架構

> 版本：1.0 ｜ 更新日期：2026-11-03 ｜ 適用：所有 SEO 網站專案 ｜ 撰寫：Claude

## 本章摘要

1. URL 是網站最早被 Google 看到的「結構訊號」：小寫、連字號、短路徑、無多餘參數、一種尾斜線規則、絕不變動——定案後寫進專案規範，改版時用對應表管理。
2. 資訊架構採「主題群集（hub-and-spoke）」：每個主題一個 hub 頁，spoke 頁與 hub 雙向連結；任何重要頁面距首頁點擊深度 ≤ 3。
3. 內部連結是你唯一能完全控制的排名訊號：錨文字描述目標頁、上下文連結優先於側欄模組、首頁權重集中給 hub 與營收頁。
4. 「會無限膨脹的 URL」（分面導覽、站內搜尋、日期封存、標籤、排序參數）必須在架構階段就決定 noindex / robots.txt / canonical 策略，否則吃掉爬取預算且稀釋索引。
5. 分頁改用「每頁獨立 canonical + 序列式 `<a href>` 連結」；`rel="prev/next"` Google 已於 2019 年停用（其他引擎仍可能參考）。

## 2. URL 規範

### 2.1 URL 結構總則

**規範**：URL 必須在上線前定案，格式為 `https://` + 單一主機名（含或不含 www 擇一）+ 小寫 + 連字號分詞 + 無追蹤參數 + 一種尾斜線規則，且日後不再更動。

**為什麼**：Google 把每一個不同字串的 URL 當成不同頁面；大小寫、尾斜線、`http`/`https`、`www`/非 `www`、參數順序不同，全部視為不同 URL，需靠 canonical 與轉址合併（Google Search Central「URL structure best practices」，查閱 2026-11-03）。每次更改 URL 都會觸發重新爬取、重新評估、連結權重經轉址傳遞的過程，流量站大規模改 URL 幾乎必然造成數週到數月的流量波動。

**怎麼做**：

| 項目 | 標準 | 範例（正確） | 範例（錯誤） |
|---|---|---|---|
| 協定 | 一律 HTTPS，HTTP 301 到 HTTPS | `https://example.com/` | `http://example.com/` |
| 主機名 | 擇一，另一個 301 | `https://example.com/` | 兩者皆 200 |
| 大小寫 | 全小寫；伺服器對大寫路徑回 301 至小寫（Linux 主機路徑大小寫敏感，不處理會產生重複） | `/best-vpn-taiwan/` | `/Best-VPN-Taiwan/` |
| 分詞 | 連字號 `-`；不用底線、空白、`%20`、駝峰 | `/how-to-pay-labor-insurance-online/` | `/how_to_pay_labor_insurance_online/` |
| 字元 | 僅 `a-z 0-9 -`；非 ASCII（中文、阿拉伯文）可用但在連結中必須 percent-encode；不要用 `.`, `,`, `'`, `&`, `+` | `/labor-insurance-rate-table/` | `/labor-insurance-rate-table-2026!/` |
| 長度 | 路徑建議 ≤ 75 字元、整段 URL ≤ 115 字元（經驗值，非 Google 規定；Google 實際上限約 2,000 字元） | — | 把整個標題塞進 slug |
| 深度 | 目錄層級 ≤ 3（不含檔名）；內容站多數文章 1–2 層 | `/topic/subtopic/article/` | `/a/b/c/d/e/article/` |
| 停用詞 | slug 可刪除 a / the / of / to，但不要刪到語意不清 | `/pay-labor-insurance-online/` | `/how-to-pay-your-labor-insurance-online-in-2026/` |
| 日期 | 一般內容 **不要** 把年份或日期放在 URL；新聞站可用 `/2026/11/` 目錄（詳見 20） | `/labor-insurance-rate-table/`（內文標年份） | `/labor-insurance-rate-table-2024/`（隔年得改 URL） |
| ID | 避免純數字 ID；若 CMS 必須帶 ID，放 slug 之後且 canonical 指向單一版本 | `/p/labor-insurance-table/` | `/p/18273/`、`/?p=18273` |
| 檔名副檔名 | 不要暴露 `.php` / `.html`（靜態站若必須，全站一致） | `/about/` | `/about.php` |
| 參數 | 僅允許「改變內容」的參數（分頁 `?page=2`、搜尋 `?q=`）；追蹤參數（utm_*、fbclid、gclid、ref）必須 canonical 回乾淨 URL | `/shoes/?page=2` | `/shoes/?utm_source=fb&sessionid=…` |
| 片段 `#` | 不得用來切換內容（Google 忽略片段）；只用於頁內錨點 | `/guide/#step-3` | `/#/products` |

**尾斜線（trailing slash）規則**：

- 二擇一：全站「目錄式」`/path/` 或「無斜線」`/path`，另一種回 301。首頁 `https://example.com/` 永遠有斜線（這是 HTTP 規範，不算衝突）。
- WordPress 預設為 `/path/`；Next.js 預設為 `/path`（`trailingSlash: true` 可改）；Astro 預設 `ignore`，部署前必須設定 `trailingSlash: 'always'` 或 `'never'`（設定細節見 15）。
- 檔案型資源（`/sitemap.xml`、`/robots.txt`、`.pdf`）不加斜線。
- 選哪一種沒有 SEO 差異；差異在於「不統一」。

**驗收方式**：

1. 用 Screaming Frog 爬全站，匯出 Internal → HTML，檢查「URL」欄：無大寫、無底線、無 `?`（除白名單參數）、尾斜線一致。
2. 手動請求 5 種變體（`http://`、大寫、無尾斜線、`www`、加 `?utm_source=test`），確認前四者 301 一跳到位、第五者 200 且 canonical 指向乾淨 URL。
3. Search Console → 頁面 → 「含有適當的標準標記的替代網頁」與「Google 選擇的標準網址與使用者不同」數量應接近 0。

**常見錯誤**：

- 上線後才發現 Linux 主機 `/About/` 與 `/about/` 同時回 200。
- 分類改名時 slug 跟著改，舊 URL 回 404 而非 301。
- 多語言站把語言放在參數 `?lang=ja` 而非路徑 `/ja/`。
- 把「2024」寫進 slug，每年更新要改 URL 或留下過期訊號。

### 2.2 多語言路徑

**規範**：多語言 / 多地區內容使用子目錄 `/{lang}/` 或 `/{lang-region}/`（例如 `/ja/`、`/en-us/`），預設語言可放根目錄或也放子目錄，但必須全站一致。

**為什麼**：Google 官方對多地區站只建議 ccTLD 或子目錄（gTLD + subdirectory），並明確不建議用參數判斷語言（Google「Managing multi-regional and multilingual sites」，查閱 2026-11-03）。子目錄共享主網域權重、維護成本最低，適合流量站。

**怎麼做**：

- 語言碼用 ISO 639-1（`en`、`ja`、`vi`、`ko`、`id`），地區碼用 ISO 3166-1 Alpha-2（`us`、`sg`、`my`）；路徑形式 `/en-us/` 或 `/us/en/` 擇一，不混用。
- 同一語言不同地區若內容幾乎相同，先不要拆（例如 `/en-us/` 與 `/en-sg/` 只差貨幣），拆了就要維護 hreflang 叢集；詳見 10。
- 預設語言是否放 `/en/`：新站建議「全部語言都有前綴」（`/en/`、`/ja/`），結構對稱、hreflang 與 sitemap 好產生；舊站已把英文放根目錄則不要搬。
- 不要用 IP 自動 301 到語言版本；只能「提示」切換（Googlebot 主要從美國 IP 爬，自動轉址會讓它看不到其他語言）。

**驗收方式**：每個語言版本在 Search Console 都能看到曝光；URL 檢查工具對 `/ja/` 頁面顯示的「Google 選擇的標準網址」是自己而不是 `/en/`。

**常見錯誤**：`/ja/` 版只翻譯一半、canonical 指回英文版（這會讓 ja 版完全不索引）；詳見 10。

## 3. 目錄與分類設計

### 3.1 目錄結構原則

**規範**：目錄結構反映「主題分類」而非「內部組織 / CMS 預設」；每個目錄層級都必須有一個可索引、有內容的 hub 頁（`/topic/` 本身回 200 且有價值），不得出現只做路徑用途的空目錄。

**為什麼**：Google 用 URL 路徑作為理解站內主題分群的弱訊號，並用目錄做 Search Console 的報表切片（「網頁」報表可按路徑篩選）。真正影響排名的是「目錄頁本身的內容與內部連結」，而非路徑字串本身——所以空目錄沒有好處，只是多一層深度。

**怎麼做**（依專案類型）：

| 專案類型 | 建議結構 | 備註 |
|---|---|---|
| 內容站 / 流量站 | `/{topic}/{article}/`，最多 `/{topic}/{subtopic}/{article}/` | 文章層級不要超過 2 層目錄；topic 頁 = hub |
| 程序化流量站（例：每個城市一頁） | `/{service}/{city}/`，或 `/{city}/{service}/` 擇一 | 以「使用者搜尋順序」決定主軸；另一軸用交叉連結而非第二套 URL（詳見 11） |
| 電商 | `/c/{category}/{subcategory}/`（分類）、`/p/{product-slug}/`（商品，不含分類路徑） | 商品不放在分類路徑下，避免一個商品多分類造成多 URL；詳見 19 |
| 企業官網 / SaaS | `/products/`、`/solutions/{industry}/`、`/pricing/`、`/blog/{slug}/`、`/docs/{section}/{page}/` | docs 可以較深，但 hub 頁必須完整 |
| 本地商家（多分店） | `/locations/{city}/{branch}/` | 每個 location 頁要有獨特內容；詳見 17 |

- WordPress：永久連結設定用「自訂結構」`/%category%/%postname%/` 僅在「一篇文章只屬一個分類」時使用；多分類時改用 `/%postname%/`，分類另有 `/category/{slug}/`（並把 `category` base 改掉或保留，但不要事後改）。
- 分類數量控制：一級分類 5–12 個；每個分類至少 10 篇以上內容再開獨立分類，否則先放在上層。
- 分類與標籤的差別：分類 = 樹狀、互斥、每篇只能一個主分類；標籤 = 橫向、可多個。標籤頁預設 noindex（見第 9 節）。

**驗收方式**：Screaming Frog「Site Structure」分頁：第 1–3 層應涵蓋 ≥ 90% 可索引 URL；Search Console 用 `/topic/` 篩選能看到每個目錄的成效。

**常見錯誤**：為了「看起來有結構」做出 `/blog/articles/category/sub/post/` 五層路徑；分類頁只有一段文字加文章列表，沒有自己的內容（hub 頁空洞）。

### 3.2 分類頁（hub）的最低內容要求

**規範**：每個分類頁 / hub 頁必須有：獨特 title、≥ 150 字的導言（說明這個主題涵蓋什麼、怎麼選讀）、依「意圖」而非「時間」排序的內容區塊、以及指向最重要 spoke 的精選連結。

**為什麼**：純列表的分類頁在 Google 眼中是「thin」且與分頁高度重複，常被歸為「已檢索 - 目前尚未建立索引」；有編輯內容的 hub 頁則可直接排名中高流量的主題詞（例如 `sss contribution` 這種 hub 詞）。

**怎麼做**：hub 頁 = 導言 + 「新手先看」區 + 子主題分組連結 + FAQ + 最新文章列表（分頁）。頁面與內容細節詳見 05。

## 4. 主題群集模型：hub-and-spoke / silo / topic cluster

### 4.1 三種模型的差異與選擇

| 模型 | 結構 | 連結規則 | 適合 | 缺點 |
|---|---|---|---|---|
| **Hub-and-spoke（主題群集）** | 一個 hub（支柱頁）+ 多個 spoke（子主題頁） | hub ↔ spoke 雙向；spoke ↔ spoke 相關時可互連 | 內容站、流量站、SaaS 部落格（推薦預設） | 要有人持續維護 hub |
| **Silo（封閉筒倉）** | 嚴格樹狀，每個主題獨立 | 只在同一 silo 內互連，跨 silo 不連 | 大型電商、多品牌站 | 過於僵硬；跨主題有關聯時反而損失相關性訊號 |
| **扁平 + 標籤** | 所有文章同層，用標籤橫向連結 | 標籤頁負責聚合 | 新聞站、小型部落格 | 標籤頁通常品質低；難以累積主題權威 |

**規範**：預設採用 hub-and-spoke；只有明確需要隔離（多品牌、多語言各自獨立團隊）時才用 silo；不採用純扁平。

**為什麼**：Google 以「主題權威」（topical authority）評估站點在某主題的整體覆蓋；群集模型讓 Google 透過內部連結理解「這 30 頁都是在講同一主題、而這一頁是總覽」，也讓連結權重在群集內流動。這是 Google 多次在 Search Central 提到的「用內部連結告訴我們哪些頁面重要」的實作方式（Google「SEO Starter Guide」內部連結段落，查閱 2026-11-03）。

### 4.2 群集設計步驟

1. **從關鍵字研究產出主題地圖**（詳見 02）：每個 hub 對應一個「頭部 / 中部詞」，每個 spoke 對應一個明確的子意圖（how-to、比較、清單、定義、工具）。
2. **決定 hub 的 URL**：hub 是 `/topic/`（目錄頁）或一篇長文 `/topic/complete-guide/`？流量站建議 **hub = 目錄頁本身**（`/labor-insurance/`），避免再多一層；企業站可用長文當 hub。
3. **每個群集最少 1 hub + 5 spoke**，最多不限；超過 30 個 spoke 時考慮拆子 hub。
4. **連結矩陣**：
   - hub → 所有 spoke（在正文中，依意圖分組，用描述性錨文字）。
   - spoke → hub（正文第一屏內出現一次 + 麵包屑）。
   - spoke → 相關 spoke（正文 2–5 個上下文連結）。
   - 跨群集連結只在內容真的相關時加；不要為了「平均分配」硬連。
5. **首頁 → hub**：首頁導覽與正文直接連到所有一級 hub（見第 5.5 節）。
6. **每季審查**：用爬蟲匯出內部連結數，找出「inlinks < 3」的 spoke 補連結；找出「沒有任何 spoke 連到的 hub」。

**驗收方式**：Screaming Frog 匯出「Inlinks」：每個 spoke 至少 3 個站內入鏈（hub + 2 篇相關），每個 hub 至少（spoke 數 + 首頁）個入鏈；Search Console 中 hub 詞的排名在 3–6 個月內應隨 spoke 增加而上升。

**常見錯誤**：hub 只放在側欄「分類」小工具裡，正文沒連；spoke 之間用「相關文章」外掛隨機推薦而非人工挑選；所有 spoke 錨文字都是「點這裡」或完全相同的關鍵字。

## 5. 內部連結規則

### 5.1 錨文字

**規範**：錨文字必須描述「目標頁的內容」，長度 2–8 個詞，同一目標頁在全站的錨文字要有 3 種以上自然變體，且不得全部使用完全一致的關鍵字。

**為什麼**：Google 明確將內部連結錨文字當作理解目標頁主題的訊號（Google「Link best practices」，查閱 2026-11-03）；全站完全相同的精準錨文字會讓內部連結看起來像操縱，且限制目標頁能對應的查詢範圍。

**怎麼做**：

- 好：`勞保 2026 年費率表`、`怎麼線上繳勞保費`、`查看完整的勞保繳費流程`。
- 不好：`點這裡`、`更多`、`文章`、整段句子當錨文字、整張圖當連結卻沒有 alt。
- 圖片連結：alt 文字即錨文字，必須寫。
- 不要在錨文字前後用 `nofollow`（內部連結永不 nofollow；要阻止爬取用 robots.txt，要阻止索引用 noindex）。

**驗收方式**：Screaming Frog「Inlinks」匯出 → 以目標 URL 分組 → 看 Anchor 欄的 distinct 數量與是否有「click here」類文字。

### 5.2 每頁連結數量與點擊深度

**規範**：正文（非導覽 / 頁尾）內部連結 3–15 個；全頁總連結（含導覽、頁尾、側欄）建議 ≤ 150；所有「需要排名」的頁面距首頁點擊深度 ≤ 3，一般頁面 ≤ 5。

**為什麼**：Google 已多年沒有「100 個連結」的硬限制，但每頁可傳遞的權重是有限的，連結越多每條越稀；點擊深度與 Googlebot 爬取頻率、以及 Google 評估頁面重要性都有相關（Google「Crawl budget」文件提到內部連結是爬取優先順序訊號，查閱 2026-11-03）。實務上深度 > 4 的頁面被完整爬取與更新的頻率明顯下降。

**怎麼做**：

- 計算深度時以「從首頁經 `<a href>` 到達」為準，JS 點擊、表單、下拉選單不算。
- 降低深度的三種手段：hub 頁在正文直接連 spoke；分頁改為「首頁連第 1、2、3 頁 + 最後一頁」；首頁 / 頁尾加「熱門主題」區。
- 內容站：1 級 = 首頁；2 級 = hub；3 級 = 文章。這表示每篇文章至少要出現在 hub 第一頁或某篇 2 級頁面裡，否則會掉到 4 級（透過分頁 `?page=7` 才到得了）。

**驗收方式**：Screaming Frog → Crawl Depth 分佈：深度 0–3 ≥ 90%；深度 ≥ 5 的 URL 清單人工審查。

### 5.3 上下文連結 vs 模組化連結

**規範**：每篇文章至少 3 個「正文中、句子裡」的上下文連結；「相關文章」模組可以有，但不能是唯一的內部連結來源。

**為什麼**：Google 對正文連結與樣板（boilerplate）連結的權重分配不同——出現在每一頁的導覽 / 頁尾 / 側欄連結被辨識為樣板，傳遞的主題訊號弱；正文中被文字包圍的連結最強。

**怎麼做**：

- 寫作規範中要求：文章第 1–2 段連 hub；每個 H2 區塊至少 1 個相關 spoke 連結；結尾「下一步」連到轉換頁或下一篇。
- 「相關文章」模組：人工指定優先於演算法推薦；若用外掛，限制在同一分類、顯示 3–6 篇、且輸出為靜態 HTML `<a href>`（不要純 JS 注入）。
- 舊文章更新時回頭加連結到新文章（「反向補連」），這是流量站最便宜、最有效的內部連結手段。

### 5.4 連結的技術要求

**規範**：所有要被爬取的連結必須是 `<a href="絕對或根相對 URL">`；不得用 `onclick`、`<button>`、`<span>`、`javascript:void(0)`、`data-href`。

**為什麼**：Google 只從 `<a>` 的 `href` 擷取連結（Google「JavaScript SEO basics」，查閱 2026-11-03）；Next.js `<Link>`、Nuxt `<NuxtLink>`、Astro `<a>` 輸出的都是 `<a href>`，正常；但自寫的 `router.push` 按鈕不會被爬。

**怎麼做**：根相對路徑 `/topic/article/` 優於父相對 `../article/`（後者在不同深度會算錯）；連結一律指向 canonical 版本（含尾斜線規則），不要連到會 301 的 URL。

**驗收方式**：Screaming Frog「Response Codes → Internal → Redirection (3xx)」應為 0；用「JavaScript rendering」模式與「Text only」模式各爬一次，比較內部連結數差異，若 JS 模式多出大量連結，表示有連結只存在於 JS 中。

### 5.5 首頁權重分配

**規範**：首頁正文（非導覽）直接連到：所有一級 hub、本季主推的 5–10 篇營收 / 策略頁、最新內容區（6–12 篇）；首頁總連結控制在 100 以內。

**為什麼**：首頁通常是外部連結最集中的頁面，它連到誰，誰就拿到最多內部權重。流量站常犯的錯是首頁只有「最新文章」列表，權重全流向隨機新文章，而真正賺錢的評測頁被埋在第 4 層。

**怎麼做**：首頁結構 = 主題入口區（hub）→ 精選 / 主推（營收頁）→ 最新內容 → 頁尾。把首頁當成「編輯精選」而不是「時間流」。

## 6. 導覽列、頁尾與麵包屑

### 6.1 主導覽

**規範**：主導覽 ≤ 7 個一級項目；下拉選單總連結 ≤ 50；以 HTML `<nav>` + `<ul><li><a href>` 輸出，在無 JS 狀態下也能看到所有連結；手機與桌機導覽內容一致（可以不同版面，但不能少連結）。

**為什麼**：行動優先索引下 Googlebot 以手機版為準（Google「Mobile-first indexing best practices」，查閱 2026-11-03）；若手機版漢堡選單少放了連結，Google 就看不到。巨型選單（mega menu）把 200 個連結塞進每一頁會稀釋權重且增加樣板比例。

**怎麼做**：導覽只放 hub 與核心轉換頁；長尾分類放在 hub 頁裡；導覽文字用使用者語言（「薪資與福利」）而非內部術語。

### 6.2 頁尾

**規範**：頁尾連結 ≤ 40；放：主要 hub（可重複導覽）、法律頁（隱私、條款、關於、聯絡——AdSense 與 E-E-A-T 必要）、語言切換、社群；不放：全站所有分類、所有標籤、關鍵字堆疊的「SEO 連結區」。

**為什麼**：頁尾是樣板，權重傳遞弱；堆疊關鍵字錨文字的頁尾在 2024 年後的 spam 政策下屬於高風險（詳見 07）。

### 6.3 麵包屑

**規範**：所有非首頁頁面都有麵包屑；格式 `首頁 › Hub › (子 Hub ›) 當前頁`；最後一項不加連結；HTML 使用 `<nav aria-label="breadcrumb"><ol><li><a>`；並同步輸出 BreadcrumbList 結構化資料（詳見 06）。

**為什麼**：麵包屑同時是使用者導航、內部連結（spoke → hub 的穩定入鏈）、與 Google 搜尋結果中顯示路徑的來源。Google 行動優先文件將 Breadcrumb 列為優先要在手機版保留的結構化資料。

**怎麼做**：

- 多分類文章：麵包屑只顯示「主分類」路徑，與 canonical URL 一致。
- 程序化頁面（`/service/city/`）：麵包屑 = `首頁 › Service › City`，讓 service hub 得到所有 city 頁的入鏈。
- 麵包屑放在 H1 上方、首屏可見；不要只放頁尾。

**驗收方式**：Rich Results Test 通過；Search Console「導覽標記」報表無錯誤；爬蟲確認每頁麵包屑連結指向 canonical URL。

## 7. 分頁、無限捲動與「載入更多」

### 7.1 現況（2026-11-03 查證）

- **`rel="prev"` / `rel="next"`**：Google 於 2019-03 宣布已多年未使用；Google 官方分頁文件目前寫明「Google 不再使用這些標記，其他搜尋引擎可能仍使用」（Google「Pagination, incremental page loading, and their impact on Google Search」，查閱 2026-11-03）。**結論：可保留（對 Bing 無害），但不要依賴它。** Next.js `metadata.pagination` 可自動輸出。
- **Googlebot 不會捲動、不會點按鈕**：只跟隨 `<a href>`。無限捲動或「載入更多」若無對應的分頁 URL，第 2 頁之後的內容 Google 找不到。

### 7.2 分頁規範

**規範**：列表類頁面（分類、標籤、搜尋、商品列表）一律提供傳統分頁 URL `?page=N` 或 `/page/N/`；每頁有自己的 canonical（指向自己，不指向第 1 頁）；每頁用 `<a href>` 連到前後頁與第 1 頁；第 1 頁 URL 不帶 `?page=1`（`?page=1` 301 到乾淨 URL）。

**為什麼**：Google 官方明確反對把所有分頁 canonical 指向第 1 頁，因為這會讓第 2 頁以後的內容（與其連出的文章）失去被爬取的路徑（同上文件）。

**怎麼做**：

| 元素 | 第 1 頁 | 第 N 頁 |
|---|---|---|
| URL | `/topic/` | `/topic/page/3/` 或 `/topic/?page=3` |
| canonical | `/topic/` | `/topic/page/3/`（自己） |
| title | `主題名 - 站名` | `主題名 - 第 3 頁 - 站名` |
| meta robots | index, follow | index, follow（預設）；若分頁內容極薄或已有 sitemap 涵蓋所有文章，可 noindex, follow，但不要 nofollow |
| 導言 | 完整 hub 內容 | 可省略或縮短（避免每頁重複 500 字） |
| 連結 | 1 2 3 … 末頁 | 1 … N-1 N N+1 … 末頁 |

- 無限捲動 / 載入更多的正確做法：UI 用 JS 載入，但同時（1）每載入一批就用 History API `pushState` 更新為 `?page=N`，（2）直接請求 `?page=N` 時伺服器回傳該頁完整 HTML，（3）頁面底部提供看得到的 `<a href="?page=N+1">` 備援連結。
- 排序 / 檢視參數（`?sort=price`、`?view=grid`）：noindex 或 robots.txt 擋掉，不要讓它們與分頁交叉相乘。

**驗收方式**：關閉 JS 存取 `/topic/?page=3` 能看到第 3 頁內容；Screaming Frog 能爬到最後一頁；Search Console「網頁」報表中分頁 URL 不應大量出現「重複網頁，Google 選擇的標準網址與使用者不同」。

**常見錯誤**：WordPress 外掛把所有分頁 canonical 指向第 1 頁；Next.js 用 `useState` 做「載入更多」但沒有 URL；分頁 URL 被 robots.txt 的 `Disallow: /*?` 一併擋掉。

## 8. 分面導覽（Faceted Navigation）與參數爬取控制

### 8.1 原則

**規範**：在架構階段把每個參數 / 分面分為三類並寫進規範：(A) 要索引的（有搜尋需求、內容獨特）、(B) 可爬但不索引的、(C) 完全不爬的；預設分類為 C。

**為什麼**：Google 2024-12 的「Crawling December: Faceted navigation」指出分面導覽是「最常見的過度爬取（overcrawl）回報來源」，會產生近乎無限的 URL、拖慢新內容被發現的速度（Google Search Central Blog，2024-12-17，查閱 2026-11-03）。

### 8.2 決策表

| 參數類型 | 範例 | 分類 | 處理方式 |
|---|---|---|---|
| 有獨立搜尋需求的單一分面 | `/shoes/nike/`、`/laptops/under-30000/` | A | 做成靜態路徑（非參數），有獨特 title / 導言 / canonical 自指，放進 sitemap |
| 多分面組合 | `?brand=nike&color=red&size=42` | C | robots.txt `Disallow: /*?*color=`、`Disallow: /*&`（擋掉任何兩個以上參數的組合） |
| 排序 | `?sort=price_asc` | C | robots.txt 擋；或若必須可爬則 noindex + canonical 至無參數版 |
| 檢視方式 | `?view=list` | C | robots.txt 擋 |
| 分頁 | `?page=3` | B（或 A） | 見第 7 節；**不要擋** |
| 站內搜尋 | `?s=`、`/search/` | C | robots.txt 擋 + noindex（雙保險，見第 9 節） |
| 追蹤參數 | `utm_*`、`fbclid`、`gclid`、`ref` | C | canonical 回乾淨 URL；可額外 robots.txt `Disallow: /*?*utm_` |
| 篩選結果為 0 筆的組合 | — | C | 回 404（Google 明確建議），不要 301 到分類首頁 |
| 工作階段 / 使用者 ID | `?sessionid=`、`?uid=` | C | 改用 cookie；robots.txt 擋 |

### 8.3 參數格式規範

- 一律用 `?key=value&key2=value2`，不要用 `;`、`:` 或路徑式假參數 `/filter/color-red/size-42/`（Google 無法辨識這是參數）。
- 同一組合的參數順序固定（程式端排序後再產生 URL），否則 `?a=1&b=2` 與 `?b=2&a=1` 是兩個 URL。
- 多值用逗號 `?color=red,blue`。
- 若分面完全不需爬取，最乾淨的做法是用 URL 片段 `#color=red`（Google 忽略片段）—— 但這會讓該狀態不可分享到搜尋結果，只適合純 UX 篩選。

### 8.4 工具狀態

- **Google URL Parameters 工具已於 2022-04 停用**（已停用）。現在只能用 robots.txt、canonical、noindex、以及 URL 設計本身控制。
- robots.txt 與 canonical 不能同時用在同一 URL：被 robots.txt 擋的頁面 Google 看不到它的 canonical 與 noindex（詳見 04）。
- Search Console「設定 → 檢索統計資料」可看到 Googlebot 花在哪些 URL 類型上。

**驗收方式**：檢索統計中「依回應」4xx 與「依目的 → 探索」佔比下降；記錄檔分析中帶 2 個以上參數的 URL 請求佔 Googlebot 總請求 < 5%。

## 9. 標籤、作者、日期封存與站內搜尋結果頁

**規範**：

| 頁面類型 | 預設處理 | 例外（可索引的條件） |
|---|---|---|
| 標籤頁 `/tag/x/` | noindex, follow | 該標籤 ≥ 10 篇、有獨特導言、對應真實搜尋需求、不與任何分類重複 → 可 index 並視為 hub |
| 作者頁 `/author/x/` | 單一作者小站：noindex；多作者站：index（E-E-A-T 用途，含作者簡介、資歷、社群連結，詳見 05 與 07） | — |
| 日期封存 `/2026/11/` | noindex, follow；並從導覽與頁尾移除「月份封存」小工具 | 新聞站可保留為可索引（詳見 20） |
| 站內搜尋結果 `?s=`、`/search?q=` | robots.txt Disallow + noindex（頁面若被間接發現也不會索引） | 無。Google 明確禁止「搜尋結果頁」被索引（詳見 07 的 spam 政策） |
| 附件頁（WordPress attachment） | 301 到所附檔案所在文章，或 noindex | 無 |
| 分頁 feed、`/feed/`、`?replytocom=` | robots.txt Disallow | 無 |
| 作者 / 標籤的 RSS、`/embed/` | robots.txt Disallow | 無 |

**為什麼**：這些頁面全是「同一批文章的不同切片」，對 Google 來說是大量重複、thin 的列表頁；Google 的 spam 政策將「自動產生的搜尋結果頁」列為「規模化內容濫用」風險項目之一；而站內搜尋若可被索引，還會被外部注入垃圾查詢字串（搜尋結果頁被用來製造含色情 / 賭博關鍵字的 URL）。

**怎麼做**：Yoast / Rank Math 都有對應開關（詳見 15）；Next.js / Astro / Nuxt 在對應 route 的 metadata 設 `robots: { index: false, follow: true }`。noindex 的頁面不要放進 sitemap。

**驗收方式**：用 `site:example.com inurl:tag` 等查詢確認結果數趨近 0（需等數週）；Search Console「網頁 → 遭 noindex 標記排除」中列出的 URL 正是這些類型（這是正常的）。

**常見錯誤**：用 robots.txt 擋標籤頁卻同時期望 noindex 生效（擋了就看不到 noindex）；把日期封存頁 noindex 但首頁側欄還是連過去幾百個月份連結，浪費爬取。

## 10. 孤兒頁偵測

**規範**：每月跑一次孤兒頁偵測；任何「可索引且有價值」的頁面都必須至少有 1 個來自可索引頁面的內部連結（不含 sitemap、不含 noindex 頁、不含分頁第 3 頁以後）。

**為什麼**：只存在 sitemap 裡、沒有內部連結的頁面會被 Google 判定為不重要，常停留在「已找到 - 目前尚未建立索引」；即使被索引，也缺乏主題訊號與權重。

**怎麼做**（三源比對法）：

1. **爬蟲 URL 集合**：Screaming Frog 從首頁爬全站（跟隨內部連結），匯出所有 HTML 200 URL（集合 A）。
2. **已知 URL 集合**：合併 sitemap.xml 所有 URL（集合 B）、Search Console「網頁」報表匯出（集合 C）、GA4 過去 90 天有曝光 / 工作階段的 landing page（集合 D）、伺服器記錄中 Googlebot 請求過的 URL（集合 E）。
3. **孤兒 = (B ∪ C ∪ D ∪ E) − A**。
4. 對每個孤兒決定：補內部連結（最常見）/ 301 合併到相關頁 / 410 移除 / 保留 noindex（例如登陸頁）。
5. Screaming Frog 可直接做：Configuration → Spider → Crawl Analysis 勾「Orphan Pages」，並連接 GSC 與 GA4 API。

**驗收方式**：孤兒頁數 / 可索引頁數 < 2%；流量站每批程序化頁面上線時，確認它們在 hub 第一頁或相關頁已有入鏈。

## 11. 爬取預算（Crawl Budget）

### 11.1 誰需要在意

**規範**：只有以下規模才需要主動管理爬取預算：≥ 100 萬個不重複頁面且每週有內容變動；或 ≥ 1 萬個不重複頁面且每天變動；或 Search Console 中大量 URL 處於「已找到 - 目前尚未建立索引」。其他站只需做好第 8–9 節的「不要製造無限 URL」（Google「Large site owner's guide to managing your crawl budget」，2026-07-22 更新，查閱 2026-11-03）。

**為什麼**：Google 定義爬取預算 = 爬取容量上限（crawl capacity limit，伺服器承受度）× 爬取需求（crawl demand，Google 想爬的程度，由已知 URL 數量、熱門度、新鮮度決定）。小站的瓶頸幾乎永遠是「需求」（內容不夠重要），不是「預算」。

### 11.2 對大型站 / 程序化流量站的優化順序

1. **消除無限 URL 來源**（分面、搜尋、日曆、排序）——第 8 節。
2. **合併重複**（canonical、301）——詳見 04。
3. **移除的頁面回 404 / 410**，不要軟性 404（回 200 的「找不到」頁）。
4. **sitemap 只放可索引 canonical URL，`<lastmod>` 必須真實**（Google 只在 lastmod 一貫可信時使用；copyright 年份變動不算更新）。
5. **縮短轉址鏈**：所有內部連結直指最終 URL。
6. **伺服器速度與 304**：支援 `ETag` / `If-None-Match` 與 `Last-Modified` / `If-Modified-Since`；Google 兩者都有時優先用 ETag（Google「How Google's crawlers work」，查閱 2026-11-03）。TTFB 快、5xx / 429 少，容量上限才會上升。
7. **內部連結優先序**：新頁面與重要頁面放在首頁 / hub 第一頁。

**沒有用的做法**（Google 文件明列）：對不想要的頁面加 noindex（Google 仍會先爬才知道）；用 robots.txt 擋頁面以「省下預算給其他頁」（除非已達容量上限，否則 Google 不會把預算挪給別頁）；`nofollow` 內部連結（Google 可能從別處發現該 URL）。

**驗收方式**：Search Console「檢索統計資料」：總檢索要求數穩定或隨內容成長；「依回應」中 200 ≥ 80%、3xx < 10%、404 < 5%、5xx ≈ 0；「平均回應時間」< 500 ms；「依目的」中「重新整理」與「探索」比例合理（新站探索高、成熟站重新整理高）。記錄檔分析（詳見 04 第 14 節）：Googlebot 請求中可索引頁佔比 > 70%。

## 12. 網站地圖與資訊架構圖的製作方法

這裡指的是「給人看的資訊架構圖」（IA diagram），不是 XML sitemap（XML sitemap 詳見 04 與 15）。

**規範**：每個專案在規劃階段產出一份 IA 文件，包含：(1) 層級樹狀圖（首頁 → hub → spoke 類型），(2) URL 模式表（每種頁面類型一列），(3) 索引策略表（每種頁面類型的 index / noindex / robots / canonical 規則），(4) 連結矩陣（哪種頁面必須連到哪種頁面）。改版前後各一份。

**怎麼做**：

1. **現況盤點（既有站）**：Screaming Frog 爬全站 → 匯出 → 用 Excel / Google Sheets 的「URL 路徑第 1 段、第 2 段」樞紐分析得到目錄層級與頁數；Screaming Frog「Visualisations → Crawl Tree Graph / Directory Tree Graph」可直接輸出圖。
2. **規劃（新站）**：從 02 的關鍵字分群結果出發，每個群集 = 一個 hub 節點，用 Mermaid 或 Miro 畫樹。Mermaid 範例（可直接放進專案 README）：

```mermaid
graph TD
  Home[首頁 /] --> Labor[/labor-insurance/ hub]
  Home --> Health[/health-insurance/ hub]
  Home --> Pension[/national-pension/ hub]
  Labor --> S1[/labor-insurance/rate-table/]
  Labor --> S2[/labor-insurance/enrollment/]
  Labor --> S3[/labor-insurance/loan/ 子 hub]
  S3 --> S31[/labor-insurance/loan/general-loan/]
  S3 --> S32[/labor-insurance/loan/disaster-loan/]
```

3. **URL 模式表**（每個專案必備，範例）：

| 頁面類型 | URL 模式 | 範例 | index | 進 sitemap | canonical | 麵包屑 |
|---|---|---|---|---|---|---|
| 首頁 | `/` | `/` | 是 | 是 | 自指 | 無 |
| Hub | `/{topic}/` | `/labor-insurance/` | 是 | 是 | 自指 | 首頁 › Hub |
| Hub 分頁 | `/{topic}/page/{n}/` | `/labor-insurance/page/2/` | 是 | 否 | 自指 | 同 Hub |
| 文章 | `/{topic}/{slug}/` | `/labor-insurance/rate-table/` | 是 | 是 | 自指 | 首頁 › Hub › 文章 |
| 標籤 | `/tag/{slug}/` | — | 否 | 否 | 自指 | — |
| 搜尋 | `/search/?q=` | — | robots 擋 | 否 | — | — |
| 作者 | `/author/{slug}/` | — | 是（多作者） | 是 | 自指 | 首頁 › 作者 |

4. **索引策略表與連結矩陣**：同上格式，列出「文章 → hub（必）」「hub → 文章（必）」「文章 → 相關文章（≥ 3）」。

**驗收方式**：開發團隊能只看 IA 文件就寫出路由、canonical、robots 設定；上線後用爬蟲比對實際結構與文件是否一致。

## 13. 改版 / 搬遷的 URL 對應表規範

### 13.1 何時需要對應表

任何會改變 URL 的動作：換網域、HTTP → HTTPS、換 CMS、改永久連結結構、改分類 slug、合併 / 拆分站點、改尾斜線規則、改語言路徑。

### 13.2 對應表格式（必填欄位）

| 欄位 | 說明 |
|---|---|
| `old_url` | 舊的完整 URL（含協定與主機） |
| `new_url` | 新的完整 URL；若頁面廢除，填 `410` |
| `type` | `301`（永久）/ `410`（移除）/ `keep`（URL 不變） |
| `old_status` | 搬遷前抓取的狀態碼（確認舊頁當時是 200） |
| `old_clicks_90d` | GSC 過去 90 天點擊（決定優先驗證順序） |
| `old_inlinks_ext` | 外部連結數（Ahrefs / GSC 連結報表） |
| `match_reason` | `same`（內容相同）/ `merged`（併入相近頁）/ `closest`（最接近主題）/ `removed` |
| `verified_at` | 上線後驗證日期與驗證者 |

**規範**：

1. 對應表涵蓋「所有」舊站 200 URL + 所有有外部連結或 GSC 曝光的 URL（含已 404 但仍有外鏈的），不只「主要頁面」。
2. 一對一優先；一對多禁止；多對一只在內容真正合併時使用，否則 Google 可能視為軟性 404。
3. **不得把大量舊 URL 全部 301 到首頁**——Google 將「不相關的轉址」視同軟性 404（Google「Redirects and Google Search」，查閱 2026-11-03）。
4. 轉址必須一跳到位；新舊站都有的中間層（例如舊站本身已有 http → https）要壓平。
5. 圖片、PDF、CSS / JS 的 URL 也要對應（圖片搜尋流量與外鏈）。
6. 舊站 sitemap 搬遷後保留 1–3 個月（內含舊 URL），讓 Google 快速重爬到 301；新 sitemap 同時提交。
7. 換網域時在 Search Console 使用「變更網址」工具（僅限網域層級搬遷）；路徑改版不需要。
8. 轉址至少保留 1 年；有外部連結的 URL 永久保留。

### 13.3 流程

1. 凍結舊站內容 → 全站爬取存檔（含 title、canonical、狀態碼、inlinks）。
2. 產出對應表 → 用腳本自動比對 slug，相似度 < 90% 的人工確認。
3. 在測試環境實作轉址規則（nginx map / `.htaccess` / Next.js `redirects()` / Cloudflare Bulk Redirects，範本見 15）。
4. 用 Screaming Frog「List mode」匯入 `old_url` 清單爬取測試環境：100% 回 301 且 `Redirect URL` = `new_url`、最終狀態 200、跳數 = 1。
5. 上線日：選低流量時段；上線後 1 小時內重跑步驟 4 對正式環境；提交新 sitemap；GSC 請求索引前 50 個高流量頁。
6. 上線後 1、7、30、90 天：GSC 比較點擊 / 曝光；爬取「依回應」中 404 應在 1 週內回到基準；監測 12 章的搬遷跌幅處理流程。

**驗收方式**：對應表每列 `verified_at` 有值；GSC 404 報表中沒有對應表內的 `old_url`；90 天後自然流量回到搬遷前 ≥ 90%（內容未變的情況下）。

**常見錯誤**：忘記對應帶尾斜線 / 不帶尾斜線的兩種舊版本；只對應了文章，分類頁與標籤頁全 404；測試環境的 `noindex` 或 `Disallow: /` 一起上線（搬遷事故第一名，詳見 12）。

## 14. 狀況 → 解法表

| 症狀 | 可能原因 | 診斷步驟 | 解法 | 預防 |
|---|---|---|---|---|
| GSC 大量「重複網頁，Google 選擇的標準網址與使用者不同」 | 大小寫 / 尾斜線 / 參數版本同時回 200；或 canonical 指向錯誤 | 抽樣 URL 用 URL 檢查看「Google 選擇的標準網址」；用 curl 測各變體狀態碼 | 統一規則 + 301；修正 canonical 為自指 | 上線前 2.1 節驗收 |
| 新文章 2 週內未被索引（已找到 - 目前尚未建立索引） | 孤兒頁 / 點擊深度太深 / 爬取需求低 | 查該頁 inlinks 數與深度 | 加到 hub 第一頁、首頁最新區、相關舊文反向補連；提交 sitemap lastmod | 發布流程納入「至少 3 個內鏈」 |
| 分類頁排名不如單篇文章 | hub 頁無內容、只有列表 | 看 hub 頁字數與獨特內容 | 補導言、分組連結、FAQ | 3.2 節 hub 最低要求 |
| 檢索統計中 Googlebot 大量請求 `?sort=`、`?color=` 等 URL | 分面 / 排序參數未控管 | 記錄檔或檢索統計依 URL 類型分析 | robots.txt 擋組合參數；0 結果回 404 | 8.2 決策表 |
| 標籤頁 / 搜尋頁出現垃圾關鍵字被索引 | 站內搜尋可索引且被外部注入 | `site:` 查詢 inurl:search | robots.txt Disallow + noindex；GSC 移除工具暫時隱藏 | 第 9 節預設規則 |
| 第 2 頁以後的文章無人爬 | 無限捲動無分頁 URL / 分頁 canonical 指向第 1 頁 | 關 JS 存取 `?page=2` | 改為獨立分頁 URL + 自指 canonical | 第 7 節 |
| 改版後流量掉 30% 以上 | 對應表不全 / 轉址鏈 / 測試環境 noindex 上線 | GSC 404 報表、爬舊 URL 清單、檢查 robots 與 meta | 補對應、壓平鏈、移除 noindex 並重新提交 | 13.3 流程逐項驗收 |
| 多語言版本互相搶排名或只有英文版被索引 | 語言版本 canonical 指向英文 / 自動 IP 轉址 | URL 檢查 `/ja/` 頁 | canonical 自指 + hreflang；移除自動 301 | 詳見 10 |
| 內部連結都是「閱讀更多」 | 樣板設計 | 爬蟲錨文字統計 | 模板改為文章標題當錨文字 | 5.1 節寫作規範 |
| 首頁權重全給了隨機新文章 | 首頁只有時間流 | 看首頁出鏈清單 | 首頁加 hub 入口與精選區 | 5.5 節 |

## 15. 本章檢查清單

**規劃階段**
- [ ] IA 文件完成：樹狀圖、URL 模式表、索引策略表、連結矩陣
- [ ] URL 規則定案：HTTPS、主機名、小寫、連字號、尾斜線、參數白名單
- [ ] 多語言路徑形式定案（`/{lang}/`）且不做 IP 自動轉址
- [ ] 每個 hub 有內容規格（導言、分組、FAQ）
- [ ] 分面 / 參數決策表完成（A / B / C 三類）

**開發階段**
- [ ] 所有變體 URL 一跳 301 到 canonical 版本
- [ ] 所有連結為 `<a href>`，指向最終 URL（無 3xx 內鏈）
- [ ] 麵包屑 HTML + BreadcrumbList
- [ ] 分頁：獨立 URL、自指 canonical、序列式連結、`?page=1` 轉回第 1 頁
- [ ] 標籤 / 日期封存 / 作者（單作者）noindex；站內搜尋 robots.txt + noindex；feed / embed / replytocom robots.txt 擋
- [ ] 手機版導覽連結數 = 桌機版

**上線前**
- [ ] 全站爬取：深度 0–3 ≥ 90%；內部 3xx = 0；無大寫 / 底線 / 非白名單參數 URL
- [ ] 孤兒頁 < 2%
- [ ] 改版專案：對應表 100% 驗證，一跳 301，舊 sitemap 保留

**營運階段（每月）**
- [ ] 孤兒頁偵測
- [ ] GSC 檢索統計：200 ≥ 80%、5xx ≈ 0、平均回應 < 500 ms
- [ ] 每季：inlinks < 3 的重要頁補連結；hub 頁內容更新
