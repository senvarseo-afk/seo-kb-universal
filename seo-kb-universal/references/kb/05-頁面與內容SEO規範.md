# 05 頁面與內容 SEO 規範

> 版本：1.1 ｜ 更新日期：2026-11-05 ｜ 適用：所有 SEO 網站專案 ｜ 撰寫：Claude

## 本章摘要

1. 頁面元素（Title、meta description、標題階層、URL、圖片）的目標是「準確描述 + 可被 Google 正確理解」，不是塞關鍵字；Google 會依據頁面內容與連結文字自行改寫標題與摘要。
2. 內容的核心判準是「滿足搜尋意圖、提供增值（information gain）」，字數不是排名因素；Google 的自評問題清單（本章第 9 節中文版）是最直接的品質量尺。
3. Google 不禁止 AI 生成內容，但「大量產出、不加價值」構成 scaled content abuse（spam policy，2024-03 起）；2026-10 起 Google 文件進一步把「無人工把關的大量 AI 產出」與「偽造作者資料」明確列為低品質。
4. E-E-A-T 不是排名因素而是評估框架；落實方式是作者頁、署名、關於頁、聯絡方式、編輯政策與引用來源，並以 `Person` / `ProfilePage` 結構化資料串接（詳見 06）。
5. 各頁面類型（文章、評論、比較、清單、工具、類別、關於）各有模板與驗收標準；本章附可打分的內容品質評分表與「狀況 → 解法」表。

## 1. Title（標題連結）

### 1.1 基本規範

**規範**：每個可索引頁面都有唯一、描述性、以頁面主題開頭的 `<title>`，品牌名放在結尾並以分隔符號隔開；長度以「在 SERP 不被截斷」為目標（英文約 50–60 字元、中文約 25–32 個全形字：業界像素推估，非 Google 規定，專案執行時以自家 SERP 實測校正），但允許為了準確而超出。

**為什麼**：Google 文件列出 title link 的來源：`<title>`、頁面主要視覺標題、`<h1>` 等標題元素、`og:title`、其他醒目文字、頁面其他文字、頁內與外部連結的錨文字、`WebSite` 結構化資料。`<title>` 是主要來源，但 Google 判斷它「半空、過時、不準確、樣板化、語言不符、重複網站名」時會改寫（來源：Google Search Central〈Control your title links in search results〉，查閱 2026-11-03）。長度數值為業界依 SERP 像素寬度（約 600px）推估，Google 只說「依裝置寬度截斷」；專案執行時以自家目標查詢的 SERP 實測校正。

**怎麼做**：
- 模式：`主要主題（含核心關鍵字）｜修飾語（年份/數量/對象）- 品牌名`。例：`目標國簽證申請流程與費用（2026 更新）- 品牌名`。
- 不以「首頁」「Home」「未命名」等空泛字做標題。
- 同站不同頁的 title 不得只差一個字（micro-boilerplate）；分頁、分類頁要動態帶入區別資訊（季數、頁碼、篩選條件）。
- 語言與文字系統必須和頁面主要內容一致（多語站詳見 10）。

**驗收方式**：
- Screaming Frog 爬站：`Title 1` 長度、重複、缺失、與 H1 相同率。
- GSC 成效報表 → 比對搜尋字詞與實際顯示標題（可用 SERP 抓取工具或手動查）；追蹤「Google 改寫比例」：抽樣 50 個主要頁面，記錄 SERP 顯示標題 ≠ `<title>` 的比例，目標 < 20%（內部基準，非 Google 數據）。
- CTR：GSC 中曝光 > 1,000 且 CTR 低於同排名中位數的頁面，優先重寫。

**常見錯誤**：關鍵字重複（「目標國簽證｜簽證目標國｜目標國簽證申請」）；全站共用同一 title；`<title>` 與可見 H1 差異太大導致 Google 改用 H1；標題放機票價格等變動資訊（Google 明示不會顯示）。

### 1.2 Google 改寫標題的機制與對策

| Google 改寫原因（官方列舉） | 症狀 | 對策 |
|---|---|---|
| 半空標題（只剩分隔符或品牌） | SERP 顯示 H1 或錨文字 | 補齊 `<title>` 的主題部分 |
| 過時標題（title 寫 2024，頁面寫 2026） | SERP 顯示新年份 | 標題與頁面可見標題同步更新 |
| 不準確（title 與內容不符） | SERP 顯示其他段落文字 | 重寫為實際描述 |
| 樣板化（多頁相同） | SERP 加入區別字（如集數） | 每頁動態帶入差異 |
| 沒有明確主標題（多個同等醒目標題） | Google 取第一個 | 讓唯一的 `<h1>` 最醒目 |
| 語言不符 | 顯示頁面其他語言文字 | 標題語言 = 內容語言 |
| 重複網站名 | 品牌名被省略 | 品牌放結尾、只出現一次 |

改完後以 GSC URL 檢查要求建立索引，生效「幾天到幾週」。若上述原因都排除仍被改寫，代表 Google 認為錨文字更能描述頁面，檢查站內連結錨文字是否一致。

## 2. Meta description 與摘要

**規範**：每頁撰寫唯一、具體、概述整頁內容的 meta description；含作者 / 日期 / 價格 / 數量等「可核實的具體資訊」；長度以不被截斷為目標（英文約 150–160 字元、中文約 70–80 全形字：業界像素推估，Google 無長度規定，專案執行時以自家 SERP 實測校正）。

**為什麼**：Google 文件：摘要主要從頁面內容擷取最符合查詢的片段，只有在 meta description「比頁面文字更準確描述頁面」時才採用它；沒有長度限制，依裝置寬度截斷。大型資料庫型網站可程式化產生，但必須可讀、彼此有差異（來源：Google Search Central〈Control your snippets in search results〉，查閱 2026-11-03）。

**怎麼做**：
- 模式：`[這頁回答什麼] + [關鍵具體資訊 2–3 個] + [範圍]`。例：「整理 2026 年目標國觀光簽證申請步驟、所需文件、費用（〇〇元起）與處理天數，附駐台辦事處地址。」
- 程式化模板（類別頁、程序化頁）：`{類別名}精選 {數量} 項：{屬性1}、{屬性2}，更新於 {日期}。`，每頁變數不同；首頁與彙整頁可用站級描述。
- 不放關鍵字清單、全站重複的 slogan、與內容無關的敘述。
- 控制摘要：`max-snippet`、`data-nosnippet`、`nosnippet`（詳見 04）。
- 「Read more」深連結（Google 2026-04 新增）：內容不藏在需點擊展開的區塊、載入時不強制捲動、不清除 URL hash。

**驗收方式**：Screaming Frog 缺失/重複/過長比例；GSC 低 CTR 頁面重寫後 4–8 週 CTR 對照；SERP 抽樣比對 Google 採用率。

**常見錯誤**：全站相同 description；只有兩三個字；為了塞關鍵字寫出不通順的句子；把 description 當排名因素（它不是，只影響 CTR）。

## 3. H1–H3 標題階層

**規範**：每頁恰好一個 `<h1>`，內容與 `<title>` 主題一致（可不完全相同）；`<h2>` 對應使用者的子問題，`<h3>` 為 `<h2>` 的細分；不跳階（h1 → h3）；標題文字描述該段內容，不做樣式用途。

**為什麼**：Google 把標題元素列為 title link 來源之一，並要求「主標題在視覺上最醒目」。標題同時是 AI Overviews / AI Mode 擷取段落的邊界（詳見 08）。標題階層也影響無障礙（螢幕閱讀器導覽）。

**怎麼做**：
- H1 = 頁面承諾（「目標國簽證怎麼辦」）；H2 = 使用者會問的子題（「需要哪些文件」「費用多少」「要多久」）；H3 = 子題內的情境分支（「台灣護照」「雙重國籍」）。
- 用問句或名詞短語，避免「第一節」「更多資訊」等空標題；H2 不要全部以相同字開頭。
- 視覺樣式交給 CSS class，不用 `<h4>` 做小字、不用 `<div class="h2">` 做標題。

**驗收方式**：Screaming Frog「H1 缺失 / 多個 / 重複」；瀏覽器擴充（HeadingsMap）檢視階層；抽樣 10 頁人工確認 H2 是否對應搜尋意圖（對照 02 的關鍵字群組）。

**常見錯誤**：Logo 用 `<h1>`；側欄「熱門文章」用 `<h2>`；全站 H1 都是品牌名；H2 全部是關鍵字變體。

## 4. URL slug

**規範**：小寫、以連字號分隔、含 2–5 個描述性字詞、不含停用詞與日期（新聞/時效內容除外，詳見 20）、不含追蹤參數；一旦發布不輕易更動，更動必須 301。

**為什麼**：URL 是使用者與 Google 判斷頁面主題的輔助線索，且是連結與分享時的可讀文本；Google 對 URL 關鍵字的權重極小，但穩定性（避免 301 鏈與失去連結）影響大。目錄結構與層級詳見 03。

**怎麼做**：
- 英文站：`/visa-requirements/`；中文站優先用英文或拼音 slug，避免百分比編碼的中文 URL 分享時過長；已有流量的中文 URL 不要為了「整潔」改掉。
- 多語站：語言目錄 + 當地語言 slug（詳見 10）。分頁用 `/page/2/` 而非 `?page=2`（詳見 03）。
- 不把類別放進文章 URL（`/travel/asia/visa/`），類別調整時會迫使改 URL。

**驗收方式**：Screaming Frog「URL 含大寫 / 底線 / 參數 / 長度 > 115 字元」；改 URL 後以 GSC 連結報表確認舊 URL 已 301 承接。

**常見錯誤**：改標題順便改 slug 而沒 301；slug 放年份；slug 塞滿關鍵字（`best-cheap-affordable-budget-hotel-taipei`）。

## 5. 圖片規範

**規範**：每張內容圖片使用描述性檔名、準確的 `alt`、明確的 `width`/`height`、響應式 `srcset`、現代格式（WebP / AVIF）與壓縮；首屏圖片不 lazy load；圖片放在相關文字旁；指定 `og:image` 或 `primaryImageOfPage` 作為代表圖。

**為什麼**：Google Images 文件：alt text 是「最重要的圖片中繼資料」，用來理解圖片主題；檔名也應具描述性；Google 不索引 CSS 背景圖；只支援 `<img src>` 可抓到的圖片；支援格式 BMP、GIF、JPEG、PNG、WebP、SVG、AVIF；2026-03 新增「preferred image」說明：Google 透過 schema.org `image`/`primaryImageOfPage` 與 `og:image` 選擇縮圖（來源：Google Search Central〈Google Images SEO best practices〉與〈Search Central updates 2026-03-02〉，查閱 2026-11-03）。圖片尺寸與 CLS/LCP 的技術規範詳見 04。

**怎麼做**：
- 檔名：`taoyuan-airport-terminal-2-arrival-hall.webp`，非 `IMG_2043.jpg`；多語站可翻譯檔名；非拉丁字元需 URL 編碼。
- alt：描述圖片內容與脈絡，10–125 字元，不堆關鍵字；裝飾圖 `alt=""`；資訊圖表的 alt 要摘要結論；inline SVG 用 `<title>`。
- 圖片位置：緊鄰相關段落，加 `<figcaption>` 說明。
- 尺寸：內文圖寬 ≥ 1,200px（供 Discover / 文章 rich result 用，Google 建議提供 16:9、4:3、1:1 三種比例且 ≥ 50K 像素）；壓縮後單張 ≤ 200KB 為目標（內部基準）。
- 代表圖：`og:image` 1,200×630；避免 Logo、文字圖、極端比例。CDN 或 JS 載入的圖片列入圖片 sitemap（詳見 04）。
- 原創圖片（實拍、截圖、自製圖表）是 E-E-A-T 與 information gain 的直接證據；庫存圖不加分。AI 生成圖片依第 10.1 節加 IPTC 中繼資料。

**驗收方式**：Screaming Frog 圖片報表（缺 alt、> 100KB、尺寸屬性缺失）；PageSpeed Insights「適當調整圖片大小」「提供新一代格式」；GSC 成效報表切換「圖片」搜尋類型看曝光與點擊。

**常見錯誤**：alt 寫「圖片」「image」；全站圖片用同一個 alt；用背景圖放產品圖；首屏主圖 lazy load 導致 LCP 變差；圖片熱連結他站。

## 6. 內文結構與可讀性

**規範**：首段（前 2–3 句、100 字以內）直接回答主要問題；每段 ≤ 4 句；每 300 字內出現一個子標題、清單或表格；數據與步驟用表格/有序清單；關鍵結論可獨立成段被擷取。

**為什麼**：Google 摘要、精選摘要與 AI 功能都從頁面擷取「能獨立回答查詢的片段」；Google 2026-05 的生成式 AI 功能指南強調「非一般性（non-commodity）內容」與清晰結構。可讀性直接影響使用者停留與回訪，是 Google 自評問題「讀完是否有滿意體驗」的實作。

**怎麼做**：
- 首段公式：`[直接答案] + [關鍵條件/例外] + [本文範圍]`。例：「台灣護照入境目標國觀光可免簽 N 天（截至 2026-11）；超過需當地延簽或事先辦簽證。本文整理三種情境的辦法、費用與時程。」
- 每個 H2 後第一段先給結論，再展開。
- 表格用於比較、規格、費用、時程，含表頭、單位、來源與日期；步驟用有序清單，並列用無序清單，每項開頭句型一致。
- 引用：具體數字與主張附來源連結（官方、原始研究優先），並標註查閱日期。
- 可讀性內部標準：每句 ≤ 40 字、每段 ≤ 150 字（中文無公認指標）；英文用 Hemingway 等級 ≤ 9。整頁無子標題、段落超過 8 行、每段同一句型開頭（AI 痕跡）都是不可讀訊號。

**驗收方式**：人工抽讀 + 評分表（第 14 節）；GA4 平均互動時間與捲動深度（90% 捲動事件）；GSC 精選摘要/AI 擷取的曝光變化（詳見 13）。

**常見錯誤**：前三段是背景鋪陳才進入答案；「在本文中我們將探討……」類空話；表格用圖片呈現；重要結論藏在折疊區。

## 7. 字數迷思與「滿足意圖」原則

**規範**：不設最低字數；長度 = 完整回答該意圖所需的最短長度。以「使用者是否不需要再回搜尋結果」為標準，而非字數。

**為什麼**：Google 文件多次表明字數不是排名因素；產品評論指南明寫「優先品質與原創性而非長度」。Google 自評問題問的是「是否提供實質、完整、全面的描述」與「相較於其他搜尋結果是否提供實質價值」——這是相對於競爭頁面的完整度，不是絕對字數。過長反而稀釋首段答案與增加閱讀成本。

**怎麼做**：
1. 先分析搜尋意圖與深度（詳見 02）：快速答案 vs. 深入研究。
2. 看前 10 名的結構，列出共同涵蓋的子題（必要）與缺少的子題（增值機會）。
3. 寫「必要 + 1–3 個增值」即可；不為湊長度加入歷史、定義、FAQ 堆砌。
4. 快速答案型（匯率、營業時間、定義）：300–600 字 + 答案區塊。深入研究型（比較、指南）：由子題數決定，通常 1,500–3,000 字；超過 3,000 字考慮拆成主題群（詳見 03）。

**驗收方式**：GSC 該頁的查詢覆蓋（是否同時獲得多個子題查詢）；GA4 平均互動時間與自訂的 pogo-sticking 近似事件。

**常見錯誤**：「競品 3,000 字所以我寫 4,000 字」；自動加 FAQ 區塊湊長度；把不同意圖塞進一頁（辦簽證 + 當地旅遊景點）。

## 8. E-E-A-T 與作者資訊

### 8.1 原則

**規範**：每篇內容有可查證的真實作者（姓名、頭像、簡介、資歷、社群連結）；網站有「關於我們」「聯絡我們」「編輯政策」「更正政策」頁；引用來源可點擊；評論類內容有第一手證據。

**為什麼**：Google 文件：E-E-A-T（經驗、專業、權威、信任）不是直接排名因素，而是品質評估者用來判斷系統是否提供好結果的框架；「信任」最重要。2026-10 更新的生成式 AI 指南明確指出「偽造作者資料（AI 頭像、虛構資歷）是欺騙，會被視為低品質」（來源：Google Search Central〈Creating helpful, reliable, people-first content〉，查閱 2026-11-03）。Google 自評「Who / How / Why」問題直接對應作者署名、製作方式揭露、創作動機。

### 8.2 怎麼做（元件清單）

| 元件 | 必要內容 | 結構化資料（詳見 06） |
|---|---|---|
| 作者署名（byline） | 姓名、發布日、更新日、連到作者頁 | `Article.author` → `Person`，`author.url` |
| 作者頁 | 真實姓名、照片、資歷/經驗（為何有資格寫這主題）、社群/外部連結、文章列表、聯絡方式 | `ProfilePage` + `Person.sameAs`、`jobTitle`、`knowsAbout` |
| 審閱者（YMYL） | 姓名、證照/資歷、審閱日期 | `Article.reviewedBy`（Google 不顯示但可用） |
| 關於頁 | 網站目的、團隊、商業模式（AdSense / 聯盟揭露）、歷史、所在地 | `Organization` |
| 聯絡頁 | 可用的 email / 表單、實體地址（若有）、回覆時效 | `Organization.contactPoint` |
| 編輯政策 | 選題、查證、更新、AI 使用、更正流程、聯盟連結是否影響評價 | 連結於頁尾與作者頁 |
| 引用來源 | 內文內嵌連結至原始來源；數據附日期 | 外部連結不需 nofollow（詳見 16） |

- 筆名可用，但要有一致人格、真實經驗證據（照片、實測）、可聯絡；不虛構資歷。外包寫手署名本人，站內編輯掛「審閱」。
- 多語站：每語言版本都有作者資訊，`Person` 用同一 `@id`。

**驗收方式**：抽樣 20 頁確認 byline 與作者頁可點；Rich Results Test 檢查 `Person` / `ProfilePage`；以「作者名 + 主題」搜尋看是否有外部提及（knowledge graph 建立跡象）。

**常見錯誤**：作者頁只有一句話「熱愛旅遊的部落客」；全站作者都是「編輯部」；AI 生成頭像；關於頁沒有任何可核實資訊；聯絡表單壞掉。

## 9. 原創性、增值與 Google 自評問題清單（中文版）

### 9.1 Information gain（資訊增益）

**規範**：每篇內容至少含一項「其他前 10 名頁面沒有」的元素：原創數據、第一手實測、獨家訪談、自製圖表/工具、在地化細節、更新的事實、明確的反面意見。

**為什麼**：Google 自評問題「是否提供原創資訊、報導、研究或分析」「是否避免只是複製或改寫其他來源」「相較於其他搜尋結果是否提供實質價值」；2026-05 生成式 AI 功能指南強調 AI 功能偏好「非一般性內容」。純彙整內容在 AI Overviews 時代最容易被取代。

**怎麼做**（增值來源清單，依成本由低到高）：
1. 在地化：目標市場的實際辦理地點、費用幣別、當地規定差異。
2. 時效：標註「2026-11 查證」並說明近期變更。
3. 第一手：實拍照片、截圖、收據、測試數據。
4. 結構化整理：把分散的官方資料整成一張對照表。
5. 原創調查 / 數據分析（也是最佳連結誘餌，詳見 16）。
6. 工具 / 計算機。

### 9.2 Google 自評問題清單（中文版）

依 Google〈Creating helpful, reliable, people-first content〉整理（查閱 2026-11-03）。用法：每篇重點內容發布前由非作者的人逐題回答「是 / 否 / 部分」，「否」超過 3 題不發布。

**內容與品質**
1. 內容是否提供原創的資訊、報導、研究或分析？
2. 是否提供實質、完整或全面的主題描述？
3. 是否提供超越顯而易見之外的洞見或有趣資訊？
4. 若引用其他來源，是否避免單純複製或改寫，而是提供實質的附加價值與原創性？
5. 主標題或頁面標題是否提供描述性、有幫助的內容摘要？
6. 主標題或頁面標題是否避免誇大或聳動？
7. 這是否是你會想加入書籤、分享給朋友或推薦的頁面？
8. 你會預期在印刷雜誌、百科全書或書籍中看到或被引用這樣的內容嗎？
9. 與搜尋結果中的其他頁面相比，是否提供實質價值？
10. 是否有拼字或文體問題？
11. 內容製作是否精良，還是看起來草率、倉促？
12. 內容是否由大量創作者大量產製或外包，或散布在大型網站網路上，導致個別頁面或網站得不到足夠關注？

**專業**
13. 內容是否以讓人想信任的方式呈現，例如清楚的來源、專業證據、作者或網站的背景資訊（如連到作者頁或關於頁）？
14. 若有人研究製作此內容的網站，會不會覺得它在該主題上受到信任或被廣泛認可為權威？
15. 內容是否由可證明熟知主題的專家或愛好者撰寫或審閱？
16. 內容是否有容易驗證的事實錯誤？

**以人為本**
17. 你是否有既有或預期的受眾，會覺得這內容對他們有用（直接造訪你的網站）？
18. 內容是否清楚展現第一手專業與深度知識（例如實際使用過產品或服務、親自造訪過地點）？
19. 你的網站是否有主要目的或焦點？
20. 讀完後，讀者是否覺得學到足以達成目標的知識？
21. 讀者讀完是否覺得有滿意的體驗？

**Who / How / Why**
22. 訪客是否能一眼看出誰寫了這內容？頁面是否有署名？署名是否連到作者的更多資訊？
23. 自動化或 AI 生成的使用是否透過揭露或其他方式對訪客顯而易見？是否說明自動化如何、為何被用於製作？
24. 製作內容的主要原因是幫助人，還是吸引搜尋引擎流量？

**驗收方式**：以上清單做成表單（Google Form / Notion），每篇記錄分數；每季抽查已發布內容。

## 10. AI 生成內容政策與使用守則

### 10.1 Google 的立場（截至 2026-11-03）

| 項目 | 現狀 | 來源 / 查閱日期 |
|---|---|---|
| 是否禁止 AI 內容 | 不禁止。Google 評估品質與意圖，不問製作工具。 | Google〈Using generative AI content〉（2025-05 新增、2026-10-01 更新），查閱 2026-11-03 |
| Scaled content abuse | 2024-03-05 起列入 spam policy：「產生大量頁面，主要為操控排名、對使用者少有或沒有價值，不論製作方式」。範例：用生成式 AI 大量產頁而不加價值；抓取後以同義詞、翻譯或混淆改寫；跨多站拆分隱藏規模。 | Google〈Spam policies〉，查閱 2026-11-03 |
| 品質評估者指引對應 | 引用 SQRG 4.6.5（scaled content abuse）與 4.6.6（少努力 / 少原創 / 少附加價值）；「大量生成文字而無人工監督或策展」= 極少努力 → 最低品質。 | 同上，2026-10 更新 |
| 偽造作者 | AI 頭像、虛構資歷 = 欺騙，頁面視為低品質。 | Google〈Creating helpful content〉，查閱 2026-11-03 |
| Spam policy 適用於 AI 回答 | 2026-05-15 起明示 spam policies 同樣適用於 AI Overviews / AI Mode 的生成式回答。 | Google Search Central updates，查閱 2026-11-03 |
| 揭露 | 「建議」在讀者合理會問「這怎麼做的」時揭露；非強制。AI 圖片建議加 IPTC `TrainedAlgorithmicMedia`（Merchant Center 強制）。 | 同上 |
| 準確性 | 生成模型會幻覺；發布前人工查核所有 AI 輸出，含標題、描述、結構化資料、alt。 | 同上 |

### 10.2 使用守則（內部規範）

**規範**：AI 可用於研究、大綱、草稿、改寫、翻譯初稿、結構化資料與摘要產生；每篇發布前必經「人審三關」：事實查核、增值確認、作者責任。未經人審的 AI 內容不得發布。

**界線表（什麼算 scaled content abuse）**：

| 行為 | 判定 | 說明 |
|---|---|---|
| 用 AI 一次產生 500 篇「X 城市最佳餐廳」且無實地資訊 | 違規風險高 | 大量 + 無增值 + 主要為排名 |
| 用 AI 把官方表格整理成對照表，人工核對數字並加在地說明 | 可接受 | 有增值、有人審 |
| 程序化頁面（詳見 11）以資料庫 + AI 文案模板產生數千頁 | 視資料獨特性 | 資料本身有價值（如自有數據）可；若只是公開資料改寫則高風險 |
| AI 翻譯整站後直接上線 | 中風險 | Google 把「翻譯後無增值」列為範例；需人工校對與在地化（詳見 10 章） |
| AI 抓取競品文章改寫 | 違規 | 「抓取後改寫」直接列於範例 |
| 跨多個網域複製同一套 AI 內容 | 違規 | 「多站隱藏規模」列於範例 |

**人審流程（最低要求）**：
1. 事實查核：每個數字、日期、名稱、法規對照原始來源並標註。
2. 增值檢查：對照第 9.1 節，至少一項增值元素；沒有就不發布。
3. 去 AI 痕跡：刪除「總而言之」「值得注意的是」等填充語；打散重複句型；加入第一手經驗。
4. 作者責任：署名者必須實際審閱並負責；不能署名未參與者。
5. 揭露：編輯政策頁說明 AI 使用範圍；AI 參與度高的頁面（自動摘要、AI 翻譯）加一句揭露。
6. 記錄：CMS 記錄「AI 參與程度」欄位（無 / 輔助 / 草稿 / 主要），供稽核。

**驗收方式**：抽查發布內容的事實查核記錄；違反 scaled content abuse 政策可能以手動處置（GSC 目前列出的類型如 Thin content with little or no added value、Pure spam）或自動降權處理；依 GSC 手動處置說明頁（查閱 2026-11-03），官方清單沒有獨立命名為「scaled content abuse」的處置類型；GSC 若出現上述手動處置，立即全站盤點。

**常見錯誤**：以「AI 偵測工具分數」作為合規依據（Google 不用這類工具，也不以 AI 偵測為標準）；只改第一段與結論就當作人審；用 AI 生成假評論/假作者；同一提示詞批量產出主題相近頁面造成自我蠶食。

## 11. YMYL 類別特別要求

**規範**：涉及健康、財務、法律、安全、重大購買決策、特定族群（YMYL）的內容，必須有具資格的作者或審閱者、引用權威一手來源、標示審閱日期、避免絕對化建議並提供免責聲明；AdSense 類流量站進入 YMYL 主題時，先評估是否有能力達標，否則不做。

**為什麼**：Google SQRG 對 YMYL 頁面要求最高的 E-E-A-T 標準；Google 文件指出 YMYL 主題的「信任」評估更嚴，缺乏專業來源的頁面可能被視為低品質。Google 的 reviews system 與 helpful content 訊號對 YMYL 的影響在核心更新中最常被觀察到（詳見 07）。

**怎麼做**：
- 作者/審閱者：醫療 → 醫師/藥師/營養師；財務 → 持證理財顧問/會計師；法律 → 律師；簽證/移民（流量站常見）→ 至少引用官方機構（移民機關、駐外館處）並標註查閱日期。
- 來源層級：官方 / 原始研究 > 同儕審查 > 權威媒體 > 其他部落格（避免）。
- 時效：每 3–6 個月審閱並更新「最後審閱日」；法規變動在內文標記「2026-XX 更新：…」。
- 免責聲明 + 可聯繫的更正管道；避免與內容衝突的廣告（詳見 09）。
- 不做：沒有專業審閱的用藥劑量、投資標的推薦、法律結論。

**驗收方式**：YMYL 頁面 100% 有審閱者欄位；核心更新前後比對 YMYL 類別的流量變化（詳見 07、13）。

**常見錯誤**：用「醫療編輯團隊」等匿名署名；引用其他部落格而非原始研究；內容明顯過時（引用已廢止法規）。

## 12. 內容時效與更新

**規範**：每頁顯示「發布日」與「最後更新日」；`datePublished` / `dateModified` 與可見日期一致並含時區；更新頻率依主題時效性分級（表）；「更新」必須是實質變更，不可只改日期。

**為什麼**：Google Article 文件建議提供 `datePublished` / `dateModified`（ISO 8601，含時區）；Google 會比對可見日期、結構化資料、sitemap `lastmod` 判斷日期，只改日期不改內容會被視為不可靠；過時標題是 Google 改寫 title 的原因之一。

**怎麼做**：

| 內容類型 | 審閱頻率 | 觸發更新的事件 |
|---|---|---|
| 法規 / 費用 / 流程（簽證、稅務） | 每季 | 官方公告、讀者回報錯誤 |
| 產品評論 / 比較 | 每 6 個月 | 新型號、價格變動、停售 |
| 常青教學 | 每年 | 介面/工具改版 |
| 新聞 / 活動 | 不更新，改寫後續報導（詳見 20） | — |
| 統計 / 數據文 | 資料來源更新時 | 年度報告發布 |

- 更新內容時：先備份並記錄原排名查詢；改寫首段答案、更新數據與截圖、頁首加「本次更新重點」、檢查內外連結、更新 `dateModified` 與 sitemap `lastmod`。
- 衰退偵測：GSC 近 3 個月 vs. 前 3 個月點擊下降 > 30% 的頁面進入更新佇列（詳見 13）。長期零曝光且無連結的頁面依第 15 節合併或刪除。

**驗收方式**：Screaming Frog 擷取 `dateModified` 與可見日期比對；GSC 更新後 4–8 週排名/點擊變化。

**常見錯誤**：WordPress 外掛自動把全站 `dateModified` 設為今天；標題寫「2026」但內文仍是 2024 的價格；只顯示更新日不顯示發布日（新聞類會被視為不透明）。

## 13. 頁面類型模板

每個模板列：必要區塊（順序）、必要元素、驗收重點。結構化資料詳見 06。

### 13.1 資訊文章（教學 / 指南 / 解釋）

1. H1 + 署名（作者、發布日、更新日）+ 代表圖
2. 首段答案區塊（≤ 100 字直接回答）
3. 目錄（> 1,500 字時）
4. H2 子題（按使用者決策順序：是什麼 → 怎麼做 → 費用/時間 → 常見問題 → 相關情境），含表格 / 步驟清單
5. 注意事項與來源
6. 延伸閱讀（站內 3–5 篇，主題群內）+ 作者簡介卡

必要：`Article`/`BlogPosting`；原創圖片 ≥ 1；來源連結 ≥ 2。驗收：首段可獨立成為精選摘要；H2 覆蓋 02 章列出的子題。

### 13.2 產品評論（Google 產品評論規範）

Google〈Write high quality reviews〉（查閱 2026-11-03）列出的做法整理：從使用者角度評估；展示專業；提供第一手證據（照片、音訊、連結）；給量化數據；說明與競品差異；涵蓋可比選項並說明各適用情境；基於原創研究談優缺點；說明相較前代的演進；聚焦關鍵決策因素；解釋設計選擇對使用者的影響；連到有用資源；連到多個賣家；「最佳」推薦需說明理由並附第一手證據；排名清單每項要有足夠實質內容。

模板：
1. H1（產品名 + 評論 + 年份）+ 署名 + 「測試方法」摘要（測了幾天、怎麼測）
2. 結論框：評分、適合誰、不適合誰、價格、購買連結（多賣家）
3. 第一手證據：實拍照片 / 測試數據表
4. H2：優點 / 缺點（各 ≥ 3，具體）
5. H2：與競品比較表
6. H2：各面向評測（依該品類關鍵決策因素）
7. H2：相較前代 / 版本變化
8. H2：常見問題
9. 聯盟揭露（頁首可見）+ 編輯獨立聲明

必要：`Product` + `Review`（含 `positiveNotes` / `negativeNotes` 可用於產品摘要，詳見 06）；聯盟連結 `rel="sponsored"`（詳見 16）。
驗收：每個「最佳」主張都有證據句；沒有實際使用的產品不寫「評論」（改為「規格比較」並明示）。

### 13.3 比較頁（A vs B）

1. H1（A vs B：哪個適合你）+ 署名
2. 首段結論：一句話分情境推薦（「預算 < X 選 A；需要 Y 選 B」）
3. 比較總表（規格、價格、適用情境、評分）
4. H2：逐項比較（每項先結論）→ 誰該選 A / 誰該選 B → 替代方案 → 方法與來源

驗收：表格可被擷取；兩方缺點都有寫；不是兩篇產品介紹拼接。

### 13.4 清單文（Best X / Top N）

1. H1（N 個 + 主題 + 年份）+ 署名 + 選擇標準摘要
2. 快速總表（名稱、適合誰、價格、評分、連結）
3. 每項目：H2 = 項目名 + 一句定位（「最佳預算選擇」）；內容含為何入選、第一手證據、優缺點、適合誰、價格、連結
4. H2：如何選擇（決策因素）→ 我們如何評選（方法、測試數量、更新日期）→ 常見問題

必要：`ItemList`（詳見 06）；每項 ≥ 150 字實質內容；項目數依意圖（不為湊數列 25 個）。驗收：Google 要求排名清單「每項足以獨立成立」。

### 13.5 工具頁（計算機 / 產生器 / 查詢）

1. H1 + 一句說明工具做什麼
2. 工具本體（首屏；JS 失效時有降級說明）
3. H2：如何使用 → 計算方式 / 資料來源 / 更新日期 → 結果怎麼解讀 + 範例 → 相關問題與延伸閱讀

必要：`WebApplication`（詳見 06）；結果可分享（URL 參數）；說明文字 ≥ 500 字供索引。驗收：JS 關閉時仍有可索引文字；是連結資產（詳見 16）。

### 13.6 類別頁 / 主題中樞頁

1. H1（類別名）+ 類別說明（100–300 字，回答「這類別涵蓋什麼、怎麼選」）
2. 子類別 / 精選內容卡片（標題 + 一句摘要）→ 列表（分頁）→ 類別導購指南（可選，不重複子頁）

必要：唯一 title/description（帶類別名與數量）；`BreadcrumbList`；`CollectionPage` 或 `ItemList`；分頁詳見 03。驗收：≥ 3 項；電商類別頁詳見 19。

### 13.7 關於頁

1. 網站是什麼、給誰、為什麼存在
2. 團隊與作者（連到作者頁）；編輯流程與 AI 使用揭露（或連到編輯政策）
3. 變現方式揭露（AdSense、聯盟）
4. 聯絡方式、營運者資訊、所在地；媒體提及 / 獎項（有才列）

必要：`AboutPage` + `Organization`（詳見 06）。驗收：第三方能從此頁核實「誰在營運」。

## 15. 重複與薄內容處理

**規範**：每個主題在站內只有一個主要頁面；內容相同或高度相似的頁面以 canonical / 301 / noindex 合併；無法補強的薄頁面刪除（410）或合併，不留「空殼頁」。

**為什麼**：重複頁分散訊號、浪費抓取預算、觸發自我蠶食；Google 的 helpful content 訊號是站級的，大量低價值頁面拖累整站評估（詳見 07）。Google 自評問題 12 直接點名「大量產製導致個別頁面得不到足夠關注」。

**怎麼做（決策樹）**：

| 情況 | 處理 |
|---|---|
| 兩頁主題相同、都有流量 | 保留較強頁，合併內容，弱頁 301 至強頁 |
| 技術性重複（參數、分頁、http/https、大小寫） | canonical 指向主版本（技術細節詳見 04） |
| 標籤頁 / 作者頁 / 日期彙整頁大量稀薄 | `noindex`（保留供使用者），或限制索引至有 ≥ 5 篇內容的標籤 |
| 薄頁面但主題有價值 | 列入更新佇列，依模板補強至評分 ≥ 27 |
| 薄頁面且主題無價值、無連結、無流量 | 410 刪除；有外部連結者 301 至最相關頁 |
| 跨語言重複（同語言不同地區） | hreflang + 在地化差異化（詳見 10） |
| 跨網域重複（多站同內容） | 違反 scaled content abuse 範例，立即去重或下線 |

- 內容稽核（每半年）：匯出全站 URL + GSC 12 個月點擊/曝光 + 連結數 + 字數 + 更新日，標記「保留 / 更新 / 合併 / 刪除」。自我蠶食以 GSC 同一查詢輪流出現不同 URL 判定。

**驗收方式**：GSC「網頁索引」中「重複，Google 選擇的標準網頁與使用者不同」數量下降；稽核後 8–12 週整站點擊變化。

**常見錯誤**：刪除有外部連結的頁面而不 301；noindex 的標籤頁仍留在 sitemap；把真正不同意圖的頁面硬合併。

## 16. 多媒體與影片嵌入

**規範**：影片放在頁面主要內容位置（首屏或緊接首段）、有文字說明與重點時間戳、以 `VideoObject` 標記；嵌入第三方（YouTube）時仍提供 `embedUrl`、縮圖、時長；非主要內容的影片不預期出現影片 rich result。

**為什麼**：Google 2023-04-13 起影片縮圖只在「影片是頁面主要內容」時顯示，2023-12 延伸至 Video 模式（來源：Google Search Central Blog〈Simplifying video presentation〉2023-04、〈Video mode now only shows pages where video is the main content〉2023-12，查閱 2026-11-03）。影片文件要求 `name`、`thumbnailUrl`、`uploadDate` 為必要；2026-09-24 新增 `creator` 屬性與 `interactionStatistic` 支援類型。

**怎麼做**：
- 影片頁：影片在首屏、頁面標題 = 影片標題、下方放逐字稿或重點摘要（可索引文字）、`Clip` 標記關鍵時刻（詳見 06）；自架影片列入影片 sitemap。
- 文章內輔助影片：放在相關段落，不期待 rich result；用 facade（點擊才載入）或 lazy iframe 降低 LCP 影響（詳見 04）。
- 音訊 / Podcast 與互動圖表：提供逐字稿或靜態圖片 + 資料表備援，確保有可索引文字。

**驗收方式**：GSC「影片頁面」索引報表（影片是否被辨識為主要內容）；Rich Results Test 的 `VideoObject` 無錯誤。

**常見錯誤**：文章頁為了 rich result 塞一支無關影片；`uploadDate` 用上傳到 CMS 的日期而非影片首次發布日；縮圖用 YouTube 預設低解析度。

## 17. 內容 → 狀況解法表

| 症狀 | 可能原因 | 診斷步驟 | 解法 | 預防 |
|---|---|---|---|---|
| SERP 標題與 `<title>` 不同 | 半空 / 過時 / 不準 / 樣板 / 與 H1 落差 / 語言不符 | 對照第 1.2 節逐項檢查；查外部錨文字 | 修正 title 與 H1 一致並重新索引 | 發布前檢查 + 每季抽樣 |
| 曝光高但 CTR 低 | 標題無吸引力、description 不具體、SERP 被 AI Overview / 影片 / 廣告佔據 | GSC 同排名 CTR 中位數；實際看 SERP 版面 | 重寫 title/description 加具體數字與差異點；版面被佔則改攻精選摘要 / AI 引用（詳見 08） | 標題模板含區別資訊 |
| 排名停在 5–15 名 | 意圖只部分滿足、缺增值、E-E-A-T 弱、內部連結不足 | 對照前 5 名列缺少子題；評分表打分 | 補子題、第一手證據、作者資訊、從主題中樞加連結 | 發布前評分 ≥ 27 |
| 核心更新後整站下滑 | 站級品質：大量薄頁、AI 量產、作者資訊缺、意圖不符 | 內容稽核（第 15 節）；比對下滑最多的類別 | 刪/合併薄頁、補強核心頁、落實 E-E-A-T；等下一次核心更新（詳見 07） | 定期稽核、不做無增值量產 |
| 收到 scaled content abuse / 純垃圾內容手動處置 | AI 或抓取量產、跨站複製 | GSC 手動處置報表；盤點受影響頁 | 移除或 noindex 違規頁、補人審、重審請求說明流程改變 | 第 10.2 節守則 |
| 同一查詢兩頁輪流排名 | 自我蠶食 | GSC 查詢 → 網頁 | 合併或明確區分意圖；內部連結指向主頁 | 發布前查站內同主題 |
| 更新後排名反而下降 | 刪掉原本獲得排名的段落 / 改 URL 沒 301 / 改了意圖 | 比對舊版（Wayback）與 GSC 查詢變化 | 恢復關鍵段落；補 301 | 更新前備份並記錄原排名查詢 |
| 產品評論文在 reviews system 更新後下滑 | 無第一手證據、只有規格改寫、「最佳」無理由 | 對照第 13.2 節逐項檢查 | 補實測、照片、比較表、方法說明；不能實測的改為非評論格式 | 評論類必須有實測記錄 |
| 精選摘要被競品拿走 | 答案區塊不夠精準、格式不對（表格/清單） | 看競品摘要格式 | 改寫答案區塊為對應格式（定義 40–60 字；步驟用有序清單；比較用表格；完整流程詳見 21 §9 S1） | 每篇設計一個答案區塊 |
| 內容被他站抄襲且對方排名更高 | 對方權威較高、Google 誤判原創 | Copyscape / 搜尋獨特句子；比對索引日期 | DMCA 移除請求；確保自站先被索引；加強原創證據（作者、日期、圖片） | 發布即提交 GSC 索引；內容含難以複製的第一手元素 |
| AI Overview 引用但無點擊 | 答案被完整摘要 | 曝光升、點擊降 | 設計「摘要之外的價值」（工具、下載、深度比較），詳見 08 | 每篇有「必須點進來的理由」 |

## 18. 本章檢查清單

**發布前（每篇）**
- [ ] `<title>` 唯一、主題在前、品牌在後、無關鍵字重複
- [ ] meta description 唯一、具體、含 2–3 個事實
- [ ] 一個 `<h1>`，H2/H3 階層正確且對應子題
- [ ] URL slug 短、描述性、無日期（非新聞）
- [ ] 首段 100 字內直接回答
- [ ] 至少一項增值元素與一項第一手證據
- [ ] 所有數字/日期有來源與查閱日期
- [ ] 作者署名、作者頁、發布日/更新日
- [ ] 圖片：檔名、alt、尺寸屬性、壓縮、代表圖
- [ ] 結構化資料對應頁面類型且驗證無誤（詳見 06）
- [ ] 內部連結 ≥ 3（詳見 03）；聯盟連結 `rel="sponsored"`（詳見 16）
- [ ] 聯盟/贊助/AI 使用揭露（適用時）
- [ ] 人審記錄：事實查核者、編輯審閱者
- [ ] 評分表 ≥ 27 分且必要項無 0 分

**每季（全站）**
- [ ] Title 改寫率抽樣 < 20%；低 CTR 頁面重寫清單
- [ ] 衰退頁（點擊下降 > 30%）更新佇列；自我蠶食檢查
- [ ] YMYL 頁審閱日期更新

**每半年**
- [ ] 全站內容稽核（保留 / 更新 / 合併 / 刪除）
- [ ] 關於頁、編輯政策、AI 揭露更新；自評問題清單抽查 20 篇
